# 팀장 신규 작업자 등록

팀장은 `/manpower/team-worker-requests`에서 신분증과 선택 사항인 통장 사진을 올리고, 분석 결과를 수정한 다음 미리보기에서 확인하여 승인 요청한다. 사무실 직원은 같은 페이지에서 신청을 검토하고 승인 또는 사유를 적어 반려한다.

## 등록 흐름

- 신분증: 이름·주소·실제로 적힌 연락처만 Gemini로 분석한다. 신분증에 연락처가 없으면 빈칸을 유지하고 직접 입력한다. 주민등록번호·생년월일·문서번호는 추출하거나 저장하지 않는다.
- 통장: 은행·계좌번호·예금주를 분석한다. 앞자리 0을 유지하며 가려진 숫자는 복원하지 않는다. 통장 없이 계좌 정보만 제출할 수 없다.
- 이미지와 PDF는 파일당 5MB까지 허용한다. 파일 첨부·드래그·모바일 촬영 입력을 제공한다. 실제 촬영 지원은 기기와 브라우저에 따른다.
- 자동 분석이 실패해도 직접 입력할 수 있다. 제출 전에 원본과 모든 필드를 확인한다.
- 소속팀은 서버에서 로그인 사용자의 연결 작업자로 조회한다. 회사는 통합DB에서 활성 청연이엔지 회사 한 개를 찾아 지정한다. 클라이언트가 다른 회사·팀을 전달해도 임의 등록할 수 없다.
- 승인을 요청할 때 `team_worker_requests`만 생성한다. 승인 트랜잭션에서 `workers` 생성과 신청 상태 변경을 함께 처리한다. 재시도·동시 승인 시 한 번만 생성한다. 본인 신청 승인은 금지한다.
- 기존 같은 이름의 연락처 또는 계좌가 일치하면 승인을 차단한다. 신규 신청 간 동시 중복은 이름·연락처 및 이름·계좌 잠금으로 방지한다. 기존 작업자를 덮어쓰지 않는다.
- 퇴사·비활성 연결 작업자는 소속팀 권한의 근거로 사용하지 않는다. 비활성 팀·회사는 신규 등록에 사용할 수 없다. 연락처는 숫자·공백·하이픈 형식만 허용하며 임의 문자를 지워 다른 번호로 저장하지 않는다.
- 조회는 신청자와 월을 서버에서 함께 제한한다. 월 변경은 작성 중인 입력을 초기화하지 않는다. 최종 확인 창이 열린 동안 배경 입력을 잠그며 페이지 종료 시 미저장 입력을 안내한다.
- 승인 성공 시 현재 화면 세션의 기존 작업자 목록 캐시를 무효화한다. 계정별 캐시는 분리하며 조회 중 계정 변경 시 이전 계정 응답을 반환하지 않는다. 이미 다른 브라우저에 열린 화면은 새로고침이 필요할 수 있다.
- 승인 재시도는 실제 `workers` 연결을 다시 검사한다. 승인 후 작업자가 수동 삭제되었다면 자동 재생성하거나 성공으로 표시하지 않고 확인 오류를 반환한다.

## 문서와 권한

`teamWorkerRequests` callable만 신청·서류를 처리한다. 현재 활성 사용자 프로필과 통합메뉴의 직책 이름을 다시 확인하며 클라이언트 역할 주장을 신뢰하지 않는다. 원본은 `team-worker-documents`에 공개 다운로드 토큰 없이 저장한다. 본인 신청 또는 사무실 검토 권한이 있는 사용자에게만 인증된 callable로 파일을 전달한다. 신청·하위 문서·원본 저장소의 직접 클라이언트 접근은 보안 규칙으로 차단한다.

통합DB 작업자에는 이름·주소·연락처·계좌·소속 정보와 `registrationRequestId`를 저장한다. 증빙 원본은 신청 검토 화면에서 확인한다. 기존 작업자 문서의 공개 URL 필드에 복사하지 않는다. 감사 이력에는 등록 근거를 기록하되 주소·계좌·신분증 사본을 중복 기록하지 않는다.

분석에는 기존 `server_settings/ai`의 API 키와 `documentModel`을 사용한다. 키는 서버에서만 읽고 요청 헤더로 전달한다. 일일 100회·분당 10회 사용자별 한도를 적용한다. 원본이나 공급자 오류 내용을 로그에 출력하지 않는다. Gemini 구조화 출력은 [공식 API](https://ai.google.dev/api/generate-content)의 `responseJsonSchema`를 사용한다.

## 통합메뉴 등록

`node scripts/register-team-worker-menu.cjs`는 변경 미리보기다. `--apply`는 원본을 로컬에 백업하고 Firestore `settings/menus_v12`를 트랜잭션으로 갱신한다. 직책 ID는 현재 설정에서 찾는다. 기존 인원관리 페이지를 `인원현황`으로 보존하고 `신규 작업자 등록` 하위 메뉴를 추가한다. 사무실에는 `작업자 등록 승인`, 관리자의 운영 관리에는 `팀장 작업자 등록 승인`을 등록한다. 재실행해도 중복하지 않는다. 라우트 카탈로그는 페이지 선택용이며 실제 사이드바 항목은 통합메뉴 DB가 소유한다.

## 검증

- 화면 테스트: 분석 결과 수정, 등록 전 미리보기, 통장 드래그, 직접 입력, 실패 후 같은 신청으로 재시도, 사무실 검토, 조회 권한 오류.
- 서버 테스트: 인증·소속팀 검증, 회사 강제 지정, 다른 신청자 서류 접근 차단, 서류 불변성, 승인 전 미등록, 동시 승인, 중복 작업자 차단, 반려, 본인 승인 금지.
- 문서 분석 테스트: 연락처 없음, 앞자리 0, 가려진 계좌번호, 요청 외 개인정보 제외, 오류에 키를 노출하지 않음.
- 메뉴 테스트: 기존 경로 보존, 현재 직책 ID 사용, 다른 메뉴 보존, 재실행 중복 방지.
- Firestore와 Storage 에뮬레이터에서 일반 사용자·관리자의 직접 조회/위조 쓰기/덮어쓰기를 거부함을 확인한다.
- 실제 Gemini 호출은 가상의 테스트 서류로만 수행한다. 실제 사용자나 통장으로 테스트하지 않는다.

`npm run functions:build` 후 `node scripts/run-team-request-tests.cjs`는 현재 프로젝트의 보안 규칙으로 두 메뉴의 가상 DB 통합 검증을 실행한다. `node scripts/audit-team-request-flows.cjs`는 운영 메뉴·소속회사·작업자 연결을 읽기 전용으로 대조하고 개인 정보 없이 건수만 출력한다.

## 운영상 남는 제한

- 신규자 승인 시 사무실이 급여 구분과 1원 이상 10억원 이하의 정수 단가를 반드시 입력한다. `workers`에 `payType`, `salaryModel`, `unitPrice`를 함께 저장한다. 지원팀·용역팀은 팀 구분과 급여 구분을 일치시킨다.
- 월별 신청은 문서 ID 순서로 100건씩 이어서 조회한다. 표시된 항목만 날짜순으로 정렬하고 필터·건수를 계산한다. 조회 중 새 신청은 새로고침으로 확인한다. 2,001건의 누락·중복 없는 전체 조회를 테스트했다.
- 신청당 업로드는 서버에서도 신분증·통장 2개로 제한한다. 실패한 업로드의 동일 파일 ID 재시도는 허용한다. 미제출 임시 신청과 첨부는 마지막 사용 후 30일이 지나면 사무실의 정리 대상으로 표시한다. 사무실에서 대상을 조회하고 건별 삭제를 확인해야 삭제한다. 서버가 삭제 직전에 기간과 상태를 다시 검사하며 제출·승인·반려 자료는 제외한다. 중간 실패는 재시도할 수 있다. 예약 자동 삭제는 실행하지 않는다.
- 신분증 번호를 분석 필드로 추출하지 않지만 원본 신분증 파일 자체에는 해당 정보가 있을 수 있다. 원본은 신청자·승인 권한자에게만 제공하며 기존 작업자 문서에 공개 URL로 복사하지 않는다.

배포 대상: `functions:teamWorkerRequests`, `firestore:rules`, `storage`, `hosting`. 기존 운영 릴리스 확인 후 검증한 변경만 배포하고 마지막으로 통합메뉴를 등록한다.
