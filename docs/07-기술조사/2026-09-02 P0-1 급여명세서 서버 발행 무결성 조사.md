## 공식 근거 — 2/3·3/3이 지켜야 할 계약

핵심 주장은 Firebase/Google Cloud 공식 페이지만 사용한다. X·블로그는 쓰지 않았다.

### 트랜잭션 read-before-write·재시도

트랜잭션은 임의의 `get()` 뒤에만 쓰기를 붙인다. 읽기는 쓰기보다 앞이어야 하고, 쓰기는 성공 커밋 끝에만 적용되며 부분 적용되지 않는다.[1] 트랜잭션 함수는 동시 수정 시 **두 번 이상 실행될 수 있고**, 애플리케이션 상태를 직접 바꾸면 안 된다.[1] 바깥에서 읽은 문서가 바뀌면 트랜잭션은 유한 횟수 재시도된다.[1]

트랜잭션 안의 읽기는 **같은 트랜잭션의 이전 쓰기를 보지 않는다.** 커밋 시각의 문서 버전만 본다.[2] 따라서 latest-head를 갱신한 뒤 같은 트랜잭션에서 head를 다시 읽어 revision을 확인하는 방식은 공식 모델과 맞지 않는다. **모든 경쟁 문서를 먼저 읽고, 그 스냅샷으로 분기한 뒤 create/update를 예약**해야 한다.[1][2][13]

경쟁이 심하면 `ABORTED: Too much contention on these documents. Please try again.` 로 실패한다.[2] 한도: 트랜잭션 요청 10 MiB, 트랜잭션 시간 270초(유휴 60초), 문서 1 MiB (1,048,576 bytes).[3]

### create-only / AlreadyExists

Node.js `Transaction.create`는 지정 위치에 문서가 있으면 **트랜잭션 자체를 실패**시킨다.[11] 반대로 `set()`은 문서가 없으면 만들고, 있으면 **내용을 덮어쓴다.**[8] 불변 아티팩트에 `set()`/`set(..., {merge:true})`를 쓰면 append-only가 아니다.

멱등 재시도: 결정적 artifactId + `create()` 실패를 이미 동일 문서로 해석. 재시도 함수 안에서 난수 ID·함수 밖 시계에 의존한 부수효과를 두면 공식 재시도 모델과 충돌한다.[1]

### callable auth 재검증

callable은 요청 본문을 역직렬화하고 Auth 토큰을 검증한다.[4] 유효하지 않은 토큰은 401 `UNAUTHENTICATED`로 거절되고, 검증된 토큰만 핸들러 context에 실린다.[5] 공식 예시는 인증 여부를 핸들러에서 다시 확인하고, 사용자 식별은 `request.auth.uid`를 쓴다.[4] **요청 본문의 uid/issuer/role을 발행 주체로 쓰면 안 된다.**

토큰 검증 ≠ 현재 권한. 폐기된 역할은 ID 토큰에 남을 수 있다. CY 기존 급여 전이는 `context.auth` 존재 확인 후 `users/{uid}` 문서를 다시 읽는다.

### 서버 시각

공식 쓰기는 `serverTimestamp()` 센티널로 **서버가 수신한 시각**을 넣는다.[8] 클라이언트 `issuedAtEpochMs`나 브라우저 시계는 불변 증빙 시각이 아니다. Functions `Date.now()`는 서버 프로세스 시계이지 Firestore 커밋 시각이 아니다. 저장 필드는 `FieldValue.serverTimestamp()`를 우선한다.

### Admin SDK와 Rules 경계

모바일/웹 클라이언트 요청만 Security Rules로 평가된다.[9] **서버 클라이언트 라이브러리(Admin SDK)는 Rules를 전부 우회**한다.[9] Functions가 `create()`로 넣더라도, 클라이언트가 같은 경로를 직접 쓰면 Rules가 막지 않는 한 위조·삭제·덮어쓰기가 된다.

겹치는 `match`는 **어느 한쪽 `allow`가 true이면 허용**이다.[6] 전용 `allow write: if false`만 넣고 generic wildcard가 true이면 쓰기가 열린다.[6] `auth != null`만으로 급여 문서를 열면 로그인한 전원에게 읽기·쓰기를 주는 형태가 되며 공식도 비권장이다.[7]

Rules 트랜잭션/배치는 전체 20 access-call, 개별 연산 10이다.[6]

1. **영속·트랜잭션 없음 (2/3 미착수)** — `materializeInitialMonthlyPayslipArtifact` (`282–349`)는 순수 함수다. `runTransaction` / `create()` / latest-head / AlreadyExists 매핑이 없다. `functions/src/index.ts`에 export도 없다. 1/3만으로 서버 발행을 완료했다고 쓰면 안 된다.

4. **권위 row identity 가드 부족** — 서버는 `payment.id === request.rowKey`만 본다 (`308`). `payment.workerId === selectedRow.workerId`, `payment.month === settlement.yearMonth`, render `workerId`/`month` nonblank canonical을 강제하지 않는다. `sourceWorkerId`/`sourceMonth`는 render에서 복사된다 (`339–340`). 클라이언트 factory는 이 일치를 강제한다 (`356–358`). 서버가 factory 스키마를 재사용하지 않는다.

5. **contractorCompanyId는 클라이언트가 고른다** — lookup은 권위 문서지만, settlement/payment의 회사와 바인딩하지 않는다 (`11–15`, `310–317`). payroll 역할이 다른 시공사 명칭을 붙일 수 있다. 제품이 선택 UI를 허용한다면 2/3에서 허용 목록·감사 필드를 명시해야 한다.

6. **시각이 의존성 주입** — `nowEpochMs` (`27`, `212`, `287–288`, `346`). 요청 본문은 아니지만 2/3 래퍼가 클라이언트 값을 넣으면 우회된다. 공식은 서버 타임스탬프다.[8]

## 데이터·보안·호환성 위험

- generic wildcard로 아티팩트 컬렉션이 열리면 활성 프로필 누구나 주민/계좌 포함 문서를 쓰거나 읽는다.
- `set()` 사용 시 재발행이 이전 불변본을 지운다.
- Admin 우회 + 열린 Rules = 서버 검증이 의미 없음.
- 1 MiB 초과 월은 커밋 실패. 사용자에게는 internal로 보일 수 있다.
- 트랜잭션 재시도 + 비결정적 시각/ID는 중복 문서 또는 해시 불일치를 만든다.

## 재현·테스트 방법 (이번 세션 미실행)
