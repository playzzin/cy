# CY 신뢰성 개선 실행 기획

상태: 진행 중인 초안. 사용자 요청에 따른 기획·로컬 검증 범위이며 배포·운영 변경 승인이 아니다.
최상위 기준: [개발지침](../개발지침.md).
관련 기획: [지원자산 저장 일관성](support-save-consistency-plan.md), [AI 기획](cy-ai-workspace-plan.md), [AI 운영 반영 기록](cy-ai-workspace-deployment.md).

## 1. 목적과 제외 범위

목적은 기능 수 증가가 아니라 날짜·금액·저장 결과를 사용자가 신뢰하게 만드는 것이다. 기존 사용자 동선을 보존하고 작은 업무 단위로 재현→수정→재검증한다.
이번 승인 범위는 심층 기획, 코드 조사, 충돌 없는 로컬 후보와 합성 시험이다. 운영 자료 조회·수정, 기능 활성화, 외부 발송, Git 공개, 배포는 자동으로 실행하지 않는다. 사용자·고객 식별정보와 실제 급여 자료를 이 문서에 저장하지 않는다.

## 2. 사실과 판단의 분리

- 기존 AI analyticsAgent의 한국 날짜/UTC 혼합 계산 오류는 이전 합성 실행에서 재현되었고 해당 코드 잔존을 재확인했다. 현재 운영 UI 도달성은 별도 추적 대상이다.
- 숙소 월대장의 필수 청구대상 조회 실패를 빈 배열로 바꾸는 코드와 개별 병렬 저장은 확인했다. 실제 UI 영향과 방어장치는 독립 조사 중이다. 아직 운영 데이터 손상으로 단정하지 않는다.
- 미사용 변수 및 React 의존성 경고 비활성화는 확인했다. 실제 버그 원인이나 라이브러리 중복의 증거와 동일하지 않다.
- AI 운영 반영 기록에는 분리된 출시 소스의 검증·배포와 전체 중지 상태가 기록되어 있다. 이번 작업에서 운영 상태를 재조회한 사실은 없다. 오래된 미배포 판정을 재사용하지 않는다.
- 다른 Codex의 변경이 존재한다. 날짜 오류 대상도 모델 정책 변경과 겹친다. 원본을 임의 수정하지 않고 충돌 없는 후보 또는 인계안으로 제한한다.
- 다른 그룹 봇의 합의를 전제로 하지 않는다. 독립 검토자는 내부 보조 검토이며 특정 봇의 발언이 아니다.

## 3. 결정 기준

우선순위는 금액·원본 손상 가능성, 실제 사용 경로, 발생 빈도, 탐지 난이도로 판단한다. 코드 길이·파일 수만으로 우선순위를 정하지 않는다.
완료 상태는 제안 / 재현 / 후보 작성 / 집중 검사 / 전체 검사 / 배포 / 실제 사용 인수로 분리한다. 이전 버전의 시험 성공을 현재 변경분의 보증으로 사용하지 않는다.

## 4. 순차 작업 묶음

### R1 — 한국 업무 날짜 일관성

사용자 결과: 오늘·지난달 조회가 접속 시각 및 브라우저 시간대에 흔들리지 않는다.
- 기존 호출 경로와 신규 AI 경로를 구분한다. 구형 경로가 미사용이면 제거 전 import·route 도달성을 확인한다.
- 기존 한국 업무일 공통 기능을 재사용한다. 저장 타임스탬프의 UTC 사용까지 일괄 변경하지 않는다.
- 이번 주 시작 요일과 최근 7일의 포함 범위는 기존 명세를 확인한다. 날짜 오류 수정에 기간 정책 변경을 섞지 않는다.
- 시험: 한국 자정 직전/직후, 오전 9시 전후, 월초/월말, 연말, 윤년, 브라우저 UTC/한국/미국 시간대. 고정 시각과 명시 기대값 사용.
- 종료 기준: 실제 계산 경로의 수정 전 실패·수정 후 정상 및 인접 회귀시험, 사용자 입력의 잘못된 날짜 거부. 후보만 만든 경우 제품 연결 여부를 별도 표시.
- 충돌 처리: 소스 소유자가 편집 중이면 기존 파일 수정 금지, 변경 제안과 시험만 인계.

### R2 — 조회 실패와 빈 자료 구분

사용자 결과: 못 읽은 자료를 정상 0건·0원으로 오해하지 않는다.
- 조회 상태를 로딩 / 정상 빈 결과 / 정상 자료 / 실패 / 오래된 자료로 구분한다.
- 필수 의존 자료가 실패하면 영향받는 계산·저장만 막는다. 독립된 보기 기능을 불필요하게 중단하지 않는다.
- 날짜·팀·숙소 이동 직후 이전 응답이 도착하는 경합을 검사한다. 정상 로드된 정확한 범위에만 저장 권한을 부여한다.
- 재시도 성공 전 기존 입력을 잃지 않는다. 이전 정상 자료는 최신 확인 실패 표시와 함께 보존하되 새 조회 결과로 표현하지 않는다.
- 시험: 권한 거절, 네트워크 오류, 빈 자료, 늦은 응답, 날짜 변경, 강제 저장 호출, 재시도 후 정상 복원.
- 종료 기준: 필수 읽기 실패 시 잘못된 합계·저장 호출 없음과 정상 빈 결과에서 합법적 신규 입력 유지.

### R3 — 부분 저장 및 안전한 재시도

사용자 결과: 무엇이 저장됐는지 알 수 있고 재시도로 중복·유실이 생기지 않는다.
- UI→서비스→저장소→파생 청구·정산을 추적하고 사용자 동작 한 번의 실제 저장 단위를 정의한다.
- 반드시 함께 반영할 항목은 원자적 처리, 독립된 항목은 항목별 결과와 실패분 재시도를 사용한다. Promise.all 자체를 원인으로 단정하거나 무조건 거대 트랜잭션으로 바꾸지 않는다.
- 원장 성공 뒤 화면 갱신·로그 실패를 원장 저장 실패로 바꾸지 않는다.
- 통신 응답 손실은 실패 확정과 구분하고 원래 요청 식별자로 확인·재시도한다. 새로운 요청으로 중복 반영하지 않는다.
- 시험: 첫/중간/마지막 저장 실패, 성공 직후 응답 손실, 이중 클릭, 두 창 수정, 조회 실패 뒤 저장, 청구 연동 실패, 확정 자료 일반 저장 거부.
- 종료 기준: 항목별 또는 묶음별 계약이 합성 저장소에서 재현되고 재조회 결과와 화면 안내가 일치. 실제 SDK 에뮬레이터 검사는 출시에 필요한 별도 단계.

### R4 — 실제 AI 사용 인수

기존 개발·배포 작업을 다시 만들지 않는다. 승인된 시범 계정과 현재 운영 상태를 확인한 후 별도 수행한다.
- 질문→해석 조건→원장 근거→표→PDF/엑셀 순서로 기간·대상·금액을 대조한다.
- 기존 화면을 무조건 정답으로 삼지 않는다. 업무 정의와 검증한 원장 기대값이 기준이다.
- 비교 근거 부족을 0원·일치로 표현하지 않는다. 과거 정산 근거를 현재 단가로 보충하지 않는다.
- 권한 축소/정지, 다운로드 직전 권한 변경, 요청 취소 및 늦은 응답을 검사한다.
- 정확도와 별도로 유효 답변 비율, 확인 질문 비율, 미지원 사유, 처리 시간과 비용을 계측한다. 현재 목표 수치를 달성 결과로 기록하지 않는다.
- 유효 확정 정산 표본이 없으면 금액 대조 미완료로 남긴다. 시험을 위해 운영 정산을 확정하지 않는다.
- 수동 조회·출력 인수 이후에만 정기 실행을 별도로 인수한다. 전체 공개·예약 활성화는 별도 승인.

### R5 — 불필요한 복잡성 정리

- 동일 업무 날짜·금액·상태에 대한 중복 계산을 먼저 식별한다.
- 중복 상태 변수는 원본 상태와 파생 상태를 구분해 줄인다. 비동기 요청 범위·사용자 입력 복구에 필요한 상태는 무작정 삭제하지 않는다.
- 변경 영역부터 미사용 변수·React 의존성 경고를 복구한다. 의존성 배열 기계적 추가로 무한 재조회가 생기지 않도록 상호작용 검사한다.
- 엑셀/표/아이콘 도구는 실제 사용처와 기능 차이 확인 후 통합한다. 제거 전 실파일 읽기/쓰기·양식 보존·빌드 크기 측정이 필요하다.
- 삭제는 미사용 확인, 대체 경로 검사, 되돌림 가능한 작은 변경 단위로만 한다. 운영 중 대규모 리팩터링 제외.

### R6 — 복구와 출시 신뢰성

- 기존 백업·복구 절차부터 조사한다. 백업 존재와 복원 성공을 구분한다.
- 별도 시험 환경에서 데이터·첨부·권한 복원 범위를 확인하고 허용 손실 범위와 복구 목표 시간을 업무 담당자가 결정한다.
- 배포 소스와 검증 소스의 동일성을 검사한다. 범위 밖 기능과 권한 변경을 함께 배포하지 않는다.
- 기능 끄기는 진행 중인 저장을 되돌리는 것과 다르므로 중지·복구 절차를 구분한다.
- 기존 기능으로 복귀할 때도 알려진 오류 경로가 재활성화되는지 검사한다.

## 5. 변경 운영과 소유권

- 현재 원본 작업 폴더와 다른 Codex 변경을 보존한다. reset/stash/일괄 정리 금지.
- 동시에 같은 제품 파일을 편집하지 않는다. 공통 설정·lockfile·배포 파일은 기존 통합 담당에게 인계한다.
- 이번 이과장 작업은 독립 조사, 개선 기획, 충돌 없는 후보·합성 회귀시험이다. 실제 변경 전 파일별 현 상태와 diff를 확인한다.
- 검토 중 소스가 바뀌면 기존 판정을 그대로 재사용하지 않는다. 검사한 후보와 인계한 후보의 동일성을 확인한다.
- 증거는 프로젝트 내 기존 관리 위치를 우선하고 사용자 개인정보·토큰·업무 원본은 기록하지 않는다.

## 6. 검증 및 출시 문턱

1. 업무 기대값 합의와 실패 재현.
2. 좁은 수정 및 집중 시험. 시험 mock이 실제 저장의 원자성·부분 실패를 숨기지 않는지 별도 검토.
3. 독립 변경 검토와 전체 typecheck.
4. 통합 담당이 기존 프로젝트 검사, Functions 빌드, 앱 빌드, Hosting 검사를 실행. 권한·저장 변경은 필요한 에뮬레이터 부정 시험 포함.
5. 승인된 시험/시범 환경에서 사용자 흐름 확인.
6. 별도 배포 승인, 정확 산출물 반영 확인, 운영 인수 및 중지 기준 기록.

문서 작성·구문 검사·개별 시험만으로 4~6단계를 통과했다고 보고하지 않는다.

## 7. 현재 실행 상태

- 기획 작성 및 독립 조사 반영: 완료. 제품 개선 전체 완료는 아님.
- R1 날짜 오류: 사용자 재개 후 로컬 제품 수정 및 집중 검증 완료, 배포 미실행. analyticsAgent.ts의 calculatePeriod가 기존 한국 날짜 도구를 재사용하도록 최소 수정하고 analyticsAgent.period.test.ts를 추가했다. 수정 전 실제 제품 분석 경로에서 9월 시작이 8월31일로 나오는 실패를 확인한 뒤 수정 후 정상 확인했다. 한국/UTC/미국 LA 각각 73개 시험 통과, 전체 typecheck 종료 0. 부모는 제품 코드·시험 코드·실제 실패/통과 로그와 최종 검사 기록을 직접 확인했다. 기존 모델 정책 변경과 공통 날짜 유틸은 보존. 기존 일요일 주 시작 및 기본 오늘-7일부터 오늘까지 의미 유지. 전체 앱 시험·빌드·운영 화면 검증은 미실행. 증거는 `.tmp/cy-date-verification/`에 보관. 초기 무관한 급여 파일 변경으로 중단했던 감시 범위는 날짜 수정 대상과 직접 의존 파일로 좁혀 재개했다.
- R2 숙소 화면 저장 보호: 로컬 수정·집중 검증 완료, 배포 미실행. UtilityLedger.tsx에 월/요청세대별 성공 로드 검사, 늦은 응답 무시, 버튼·핸들러 및 비동기 사전검사 이후 저장 직전 방어, 행 월 검사, 원장 성공 후 후속 실패 안내 분리를 추가했다. 신규 UtilityLedger.loadGuard.test.tsx 14개 및 인접 시험을 합해 10개 묶음/96개 통과, 전체 typecheck 종료 0 기록. 부모는 task-only.diff와 실제 실패(금지된 저장 1회)/최종 통과 로그를 직접 확인했다. 서비스 모킹 시험으로 호출 차단을 검증한 것이며 DB 원자성이나 운영 UI 인수를 보장하지 않는다. 증거 `.tmp/cy-accommodation-load-guard/`.
- R2 잔여: listTargets 및 getMonthlyLedger의 이중 오류 은폐 미수정. 서비스에서 성공 빈 목록으로 바뀐 실패는 이번 화면 보호가 구별할 수 없다.
- R3 잔여: 대장 다건 저장의 원자성, 다른 사용자 동시 수정, 저장 완료 뒤 월 이동과 후속 청구 처리의 전체 동작은 미해결/추가 검증 대상. 기존 billingSyncPending·자동청구·보상 로직은 보존.
- R4~R6: 계획 수립, 이번 실행 미착수.

### 독립 조사에 따른 설계 보강

아래는 보조 검토의 소스 추적 결과이며 운영 장애 발생의 증거가 아니다. 병행 변경 중이므로 구현 전에 최신 소스를 다시 읽는다.

1. **이중 오류 은폐 제거:** accommodationBillingTargetService.listTargets의 일반 Firestore 경로 자체도 오류를 빈 배열로 바꾼다. getMonthlyLedger의 바깥 catch만 제거해서는 부족하다. scoped/direct 양쪽을 엄격한 조회 계약으로 맞추고 기존 소비자 영향을 조사한다. UtilityLedger의 별도 청구대상 조회와 대장 내부 조회는 성공한 동일 결과를 사용하도록 조립한다.
2. **현재 월 저장 경계:** UtilityLedger의 로드 실패는 이전 records를 보존하고 reviewLoadError는 일부 검토 UI에만 적용된다. 저장 버튼과 핸들러에서 로드 성공한 월·요청 세대·행 월 일치를 함께 확인한다. 월 이동 후 이전 응답의 성공/실패 모두 무시하고 초안은 범위별 보존한다. 저장 완료 뒤 재조회 실패는 저장 실패와 분리한다.
3. **부분 저장 범위:** saveUtilityRecords는 개별 merge setDoc를 병렬 호출한다. 첫 거절 후 나머지 쓰기는 계속될 수 있어 재시도와 겹친다. UI 일괄 저장이 하나의 묶음이라는 업무 기준을 확정하면 모든 행 선검증 후 단일 batch commit 후보를 적용한다. 허용 크기 초과 시 쓰기 전 거부하고 조용히 분할하지 않는다. 이것만으로 동시 편집이나 대장→청구 전체 원자성이 해결되지는 않는다.
4. **기존 복구장치 보존:** 결정적 ID, 중복 제거, billingSyncPending 및 후속 청구 트랜잭션이 이미 존재한다. 복구장치가 없다고 보고하거나 삭제하지 않는다. 초기 부분 실패에서도 정확한 상태 표시·재조회·재시도와 연결되도록 검증한다.
5. **필수 재현 사례:** 계약 1월/청구대상 7월/조회 6월에서 조회 실패가 기본 행을 생성하지 않는지, 이전 월 자료+새 월 실패에서 강제 저장도 거부되는지, A 성공/B 실패/C 지연 성공과 재시도 경합, batch 실패 전부 미반영, 대장 성공 후 청구 실패 marker 복구를 합성 시험한다.
