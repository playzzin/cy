# Android · 카카오톡 사진 공유 검수

2026-10-17 사용자가 Android 휴대전화와 팀장·테스트 팀원 계정을 현재 준비하기 어렵다고 확인했다. 실제 공유창·카카오톡 수신과 운영 승인·재로그인 검수는 대기 상태다. PC 브라우저나 에뮬레이터 결과를 실기기·운영 통과로 계산하지 않는다.

## 준비된 자료

- `artifacts/client-workflow-qa/android-kakao-synthetic.png`: 1200×760 합성 이미지. 실제 신분증·급여·서명·계좌를 포함하지 않는다.
- `fixtures/client-mobile-preview/sharePhoto.ts`: 한글·숫자·방향·색상을 식별할 수 있는 이미지 생성 원본.
- `artifacts/client-workflow-qa/photo-results.json`: 실제 PNG 다운로드, 파일 바이트 비교, 공유 인자·취소 검사 결과.
- 공유·취소 검사는 실제 `ImageFileActions`를 사용하되 브라우저의 `navigator.share`만 대체했다. 네이티브 카카오톡 호출은 실행하지 않았다.

## 연결 가능할 때 실행

1. 운영 배포 커밋과 검수에 사용할 컴포넌트 소스의 일치부터 확인한다. 기존 `scripts/client-mobile-preview.cjs`는 원래 작업 폴더의 소스를 사용하므로, 배포 작업 트리의 최신 소스로 연결한 후 실행해야 한다. 화면에는 합성 자료만 표시한다.
2. 휴대전화 USB 연결·디버깅을 허용한 뒤 Android SDK의 `adb devices`로 해당 기기 한 대를 확인한다. 여러 기기면 `-s <serial>`로 대상을 지정한다.
3. `adb reverse tcp:4193 tcp:4193` 후 휴대전화 Chrome에서 `http://127.0.0.1:4193/?preview=photo`를 연다. 이 절차는 연결 가능한 시점에 수행하며 현재 실행하지 않았다.
4. `사진 공유·저장`을 눌러 전체 사진과 한글·숫자·색상 네 칸을 확인한다.
5. `공유창 열기`가 보이면 눌러 카카오톡을 선택한다. 검수자가 정한 테스트 채팅방에서 수신 결과를 확인한다. 파일 한 장이어야 하며 웹주소·별도 설명이 함께 붙지 않아야 한다.
6. 공유창에서 취소한 후 `공유를 취소했습니다.` 안내와 재시도를 확인한다.
7. 공유창 버튼이 없거나 공유가 실패하면 `사진 저장` 후 갤러리에서 사진으로 첨부한다. 수신 이미지의 방향·내용·가독성을 확인한다. 원본 파일 전달 검수와 카카오톡의 압축 옵션 검수를 구분한다.
8. 이미지 복사 기능이 제공되는 환경에서는 복사 후 테스트 채팅 입력란에 붙여넣기를 확인한다. 미지원 안내가 표시되면 저장 대안을 사용한다.
9. 검수 후 `adb reverse --remove tcp:4193`로 이 테스트 포트 연결만 해제한다.

## 두 사진 경로를 따로 확인

|경로|검수 동작|통과 기준|
|---|---|---|
|신분증 이미지|실제 신분증 대신 합성 이미지를 넣고 `사진 공유·저장` → `공유창 열기` → 검수자가 지정한 테스트 채팅방|사진 1장만 수신, 웹주소·별도 설명 없음, 방향·한글·숫자 정상|
|급여명세서|합성 작업자·금액으로 만든 명세서에서 `카톡·공유` → 캡처 미리보기 → `공유창 열기` → 같은 테스트 채팅방|사진 1장만 수신, 웹주소·별도 설명 없음, 선택한 작업자·월 일치, 명세서 내용 잘림 없음|

두 경로 모두 공유 취소 후 재시도와 사진 저장 대안도 확인한다. `navigator.share` 호출 성공이나 공유창 닫힘만으로 수신 완료를 판정하지 않는다. 기존 `photo-results.json`은 일반 이미지 파일 공유의 대체 API 검사이며, 급여명세서의 실제 Android 캡처·카카오톡 수신 검사까지 대신하지 않는다. 현재 합성 이미지 외에 운영 고객 사진·명세서를 사용하거나 전송하지 않았다.

## 팀원 승인·재로그인 운영 검수 순서

준비물은 실제 팀장 계정과, 그 팀에 소속된 기존 일반 작업자에 연결 요청한 승인 대기 테스트 팀원 계정 1개다. 계정 비밀번호는 채팅이나 결과 문서에 기록하지 않고 사용자가 브라우저에서 직접 로그인한다. 팀장 메뉴 미리보기와 실제 팀장 권한 검증을 구분한다.

1. 테스트 팀원 로그인: 승인 전에는 업무 화면 대신 승인 대기가 표시되는지 확인한다.
2. 팀장 로그인: `팀원 계정 승인`에서 사용자에게 지정받은 테스트 팀원 1개가 보이는지 확인한다. 동명이인이 있으면 팀과 계정 연결을 먼저 식별한다.
3. 지정한 테스트 요청만 선택하여 실제 승인 대상으로 검토한다. 다른 운영 계정을 선택하거나 일괄 승인하지 않는다.
4. 승인 결과와 계정 권한 반영 상태를 구분해 확인한다. 권한 반영 대기라면 완료로 기록하지 않는다.
5. 테스트 팀원을 완전히 로그아웃한 뒤 별도 브라우저 세션에서 같은 계정으로 직접 로그인한다. 승인 대기 없이 허용된 업무 화면에 들어가는지 확인한다.
6. 한 번 더 로그아웃·로그인하여 새 승인 요청이 생기지 않는지 확인한다. 타팀 자료·사무실 메뉴가 열리지 않는지도 확인한다.
7. 결과에는 통과 여부·일시·환경과 필요한 오류 코드만 기록한다. 비밀번호·토큰·실제 개인 정보는 저장하지 않는다. 승인된 테스트 계정의 사후 처리 여부는 별도 결정하며 임의 삭제·권한 변경을 하지 않는다.

현재 상태: 두 항목 모두 실사용 검수 미실행. 기존 로컬 승인·별도 브라우저 재로그인 통과 기록은 `artifacts/client-workflow-qa/flow-results.json`에 있으며 운영 검수 결과와 구분한다.
