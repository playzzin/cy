# 신규자·경비 입력 후속 검증

## 완료한 개선

- 월별 신청을 100건씩 이어서 조회하도록 변경했다. 기존 2,000건 한도를 제거하고, 현재 불러온 항목 기준으로 필터·합계를 표시한다. 문서 ID 순서로 조회하므로 승인 상태 변경으로 조회 위치가 움직이지 않는다. 조회 중 새 신청은 새로고침으로 확인한다.
- 신규자 승인에는 사무실의 급여 구분·단가 입력이 필요하다. 승인 트랜잭션에서 기존 workers 문서에 payType·salaryModel·unitPrice를 함께 기록한다. 잘못된 값, 0원, 지원팀/용역팀 구분 불일치는 서버에서 거부한다.
- 마지막 사용 후 30일 이상 된 미제출 자료는 사무실이 조회하고 건별 확인 후 정리할 수 있다. 제출·승인·반려 자료는 제외하며, 최근 재사용한 신청은 삭제 직전 다시 보호한다. 부분 실패는 재시도할 수 있다. 자동 예약 삭제는 도입하지 않았다.

## 실제 검증

- 화면·서비스 테스트 43건, 영수증 분석·카메라 테스트 6건 통과.
- 격리된 Firebase 데모 환경의 서버·분석·보안 규칙 테스트 15건 통과. 2,001건 전체 조회, 동일 신청 동시 승인, 기존 DB 등록, 급여 저장, 임시 파일/하위 문서 삭제, 제출 파일 보존 포함.
- 기존 메뉴 보존·중복 방지 테스트 2건 통과. 총 66건.
- TypeScript 검사, 수정 파일 ESLint, Functions 빌드, 전체 프런트엔드 프로덕션 빌드 및 릴리스 기록 생성 통과.
- 운영 DB는 읽기 전용으로 조회했다. 월별/사용자별 페이지 조회와 정리 대상 조회 인덱스가 정상 작동한다. 신규자 신청/등록 작업자는 모두 0건이다.
- localhost의 두 페이지를 실제 브라우저에서 열었으며 실행 오류 로그는 없었다. 현재 브라우저는 개발 샘플 계정이므로 실제 계정 로그인 안내까지 확인했다.

## 운영 반영 전 조건

- 운영 저장/승인을 실제 사용자로 수행한 것은 아니다. 운영 DB에 테스트 자료를 추가하거나 실제 임시 자료를 삭제하지 않았다.
- 이번 변경은 로컬 코드이다. 신규자 승인 요청 형식에 payroll이 추가되므로 화면과 서버 함수를 함께 반영해야 한다.
- 운영 배포 스크립트 scripts/deploy-verified.cjs는 커밋되지 않은 작업 트리를 거부한다. 현재 다른 작업의 미커밋 변경이 다수 섞여 있으므로 이번 검증을 전체 변경의 운영 배포 승인으로 간주하지 않는다. 범위를 분리한 릴리스와 실제 계정 검증이 필요하다.

## 실제 테스트 계정 브라우저 검증

격리 프로젝트 demo-team-browser의 Auth/Firestore/Storage/Functions 에뮬레이터와 별도 개발 화면(3015 포트)을 사용했다. 운영 계정 권한을 바꾸거나 운영 DB에 테스트 자료를 쓰지 않았다.

- 이메일/비밀번호로 테스트 팀장 계정에 실제 로그인하고 두 메뉴가 입력 화면으로 표시되는 것을 확인했다.
- 소속 A팀에서 B팀으로 가상 경비 12,345원을 제출했다. AI 키가 없는 경우 분석 오류 안내 후 직접 입력으로 계속할 수 있었다.
- 개인정보 없는 가상 이미지와 이름·주소·연락처로 신규자를 제출했다. 두 신청 모두 pending이며 이 시점의 경비 원장/신규 등록 작업자는 0건이었다.
- 별도 사무실 테스트 계정으로 로그인했다. 신규자 급여 미입력 승인은 차단됐고, 일급제/150,000원 입력 후 승인됐다. 경비 역시 승인 확인창을 거쳐 처리됐다.
- DB를 별도 대조했다. workers에 신청 연결을 가진 신규자 1명과 급여 구분·단가가 저장됐고, team_expense_claims에 신청 연결을 가진 경비 1건과 12,345원이 저장됐다.
- 팀장으로 다시 로그인해 승인 결과가 유지되고 승인 버튼은 보이지 않는 것을 확인했다.
- 실제 Auth 에뮬레이터 로그인 토큰으로 두 callable에 직접 요청하여 사무실 승인, 임시 자료 정리, 다른 팀 명의 업로드가 모두 PERMISSION_DENIED인 것을 확인했다.
- Google 로그인은 기존 계정을 자동 재선택하지 않도록 prompt=select_account를 추가했다. 실제 Google 계정 선택창이 표시되는 것까지 확인했다. TypeScript·ESLint·전체 빌드 통과.

이 검증은 실제 화면과 인증·서버 함수를 사용하는 데모 환경 검증이며 운영 배포/실제 사용자 증빙 검증과 구분한다.

## 2026-09-21 DB 직책 직접 변경 검증

scripts/verify-team-request-roles.cjs로 별도의 데모 인증 계정을 생성하고 DB의 position을 작업자 → 동적 직책 ID(팀장) → 동적 직책 ID(사무실) → 팀장으로 변경했다. 연결 작업자의 역할은 작업자로 고정하고 관리자 인증 클레임은 부여하지 않았다.

실제 이메일/비밀번호 로그인에서 받은 동일 인증 세션으로 두 callable을 호출했다. 일반 직책은 PERMISSION_DENIED, 팀장은 canReview=false와 소속팀 1개, 사무실은 canReview=true, 팀장 복귀 시 canReview=false를 확인했다. 각 변경값은 DB를 다시 읽어 확인했다. 메뉴 모드나 위조 역할 입력으로 테스트하지 않았다. 테스트 종료 후 생성한 가상 계정과 작업자·팀·회사는 정리했다. 운영 계정의 직책은 변경하지 않았다.
