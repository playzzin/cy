# CY 클라이언트 모바일 요구사항 순차 실행 계획

팀장은 담당 현장과 팀원의 공수를 쉽게 조회하고 필요한 신청만 한다. 사무실은 일보 입력, 공수 정리, 가불 검토와 지급, 정산을 담당한다. 기존 React와 Firebase 구조 및 금액 계산을 활용하면서 모바일 화면과 역할별 업무 범위를 정리한다.

이 계획은 첨부된 고객 대화와 현재 로컬 소스를 기준으로 한 구현안이다. 요구사항은 아래 R01부터 R18까지 추적한다. 체크박스는 앞으로의 완료 조건이며 현재 구현 또는 운영 반영 완료를 뜻하지 않는다. 원본 대화의 실명, 신분증, 서명, 급여 자료는 이 문서에 옮기지 않는다.

실행 결과는 [구현·검수 기록](./client-mobile-workflow-implementation-report.md)에서 단계별로 관리한다. 전체 라우트의 디자인 적용 결정은 [312개 라우트 목록](./client-mobile-route-design-inventory.md)에 기록했다. 아래 계획상의 실기기·운영 검수를 로컬 코드 구현 완료와 혼동하지 않는다.

2026-10-16 현재 핵심 기능 구현 후 실제 전체 앱과 로컬 Firebase를 연결해 계정 승인·재로그인·가불 접수·지급 상태·정산 월 이동을 검증했다. 312개 경로의 390/1366px 진입·캡처·넘침 검사를 완료했고, 수정한 39종 화면을 추가 검수했다. 아래 체크리스트는 최초 검수 기준으로 보존하고 최신 자동 검사와 빌드 결과는 구현·검수 기록을 따른다. 모든 경로의 모든 데이터·권한 상태를 검증한 것은 아니다. 실제 Android·카카오톡 검수는 사용자가 현재 휴대전화를 연결할 수 없어 남겨두며, 운영 E2E와 배포는 별도다.

기획 범위는 기존 번호를 유지한 **03~13의 11단계**다. 별도 기준 상태 조사와 업무 정책 수립 단계는 제외한다. 구현에 필요한 기존 코드·권한·데이터 확인은 해당 기능 작업 안에서 수행한다.

실행 순서는 **03 공통 모바일 구성 → 04 작업자 조회 → 05 현황판 → 06 신분증 공유 → 07 정산 월 선택 → 08 가불 → 09 팀원 계정 승인 → 10 메뉴와 접근 제한 → 11 기능 검수 → 12 전체 디자인 → 13 최종 검수**다. 각 단계는 완료 조건과 검증 결과를 충족한 뒤 다음 단계로 진행한다.

## 기능별 적용 기준

아래 기준을 각 기능 단계에서 적용한다. 별도 정책 수립 작업을 선행하지 않는다. 기존 권한이나 데이터 의미가 불명확한 경우 해당 기능의 실제 코드와 화면을 확인하고, 사용자 결정이 꼭 필요한 경계만 해당 단계에서 확인한다.

| 구분 | 기본안 | 확인이 필요한 경계 |
| --- | --- | --- |
| 팀장 조회 | 현재 서버에서 허용한 담당 팀·현장 범위 | 전체 선택은 회사 전체 열람 권한을 뜻하지 않음 |
| 작업자 상태 | 전체 기본, 재직·퇴사 빠른 선택 | 비활성·출입금지 등 기존 상태를 임의로 퇴사로 합치지 않고 현재 정의 확인 |
| 일보·공수 | 팀장은 조회, 사무실은 원천 입력과 수정 | 메뉴 제거가 사무실의 업무 기능까지 제거하지 않음 |
| 근무 내역 | 작업자 상세에 근무내역 영역으로 통합 | 독립 개인달력·출력일보 메뉴는 없애되 달력 조회는 유지 |
| 가불 | 본인 신청과 기존에 허용된 소속 팀원 대리 신청 유지 | 이 작업에서 대리 신청 대상을 확대하지 않음 |
| 가불 처리 | 접수·승인·반려·지급완료는 기존 사무실 흐름 사용 | 신청 자동 등록은 자동 승인·자동 지급이 아님 |
| 계정 승인 | 기존 작업자와 소속팀이 검증된 계정의 연결 승인 | 신규 작업자 통합DB 등록 승인과 계정 연결 승인을 구분 |
| 승인 유지 | 최초 연결 승인 이후 정상 로그인은 재승인 없음 | 현재 불편이 매번 로그인 문제인지 신규 가입 누적인지 먼저 재현 |
| 퇴사·팀 이동 | 현재 소속에 따라 접근을 재평가하고 이전 팀 접근 제거 | 팀장에게 전사 계정 삭제·권한 변경 권한을 부여하지 않음. 계정 전체 정지는 사무실 정책 확인 |
| 메뉴 정리 | 대상 팀장 역할에 적용 | 일반 작업자·사무실 등 다른 역할의 휴무 메뉴까지 없앨지는 별도 범위 확인 |
| 현황판 밀도 | 휴대폰 기본 2열 | 3열에서 이름과 숫자가 읽히지 않으면 상세가 축약된 작은 보기로만 제공 |
| 전체 디자인 | 기능 개선 후 별도 묶음으로 적용 | 첨부의 작은 참고 이미지로 세부 글꼴·간격을 추정해 전면 적용하지 않음 |

팀장 메뉴 기본 구조는 **현황 / 인원 / 가불 신청 / 정산 / 팀원 승인**이다. 급여명세서와 신분증은 인원 영역에서 접근하고, 현재 필요한 신규 작업자 등록은 별도 폐기 요청이 없으므로 보존한다. 기존의 다른 업무 메뉴는 이번 제거 대상 목록과 구분한다.

## 단계별 실행 작업

### 03 공통 모바일 구성 마련

시작 단계다. 기존 컴포넌트와 화면 구성을 확인하면서 진행한다. 전체 테마 변경은 12에서 진행하고 여기서는 다음 화면에 필요한 공통 요소만 만든다.

- [ ] 기존 MonthNavigator를 활용해 상시 노출 조회월 선택줄을 정의한다.
- [ ] 검색·상태 선택·요약 수치의 공통 배치를 정한다.
- [ ] 기존 대화상자 구성요소를 우선 사용해 모바일 하단 상세창을 마련한다.
- [ ] 헤더 높이, 상단 고정 영역, 하단 내비게이션, 키보드 표시 시 겹침을 점검한다.
- [ ] 화면 전체 확대/축소나 고정 비율 축소 대신 여백과 반복 요소를 줄인다.
- [ ] 주요 버튼은 44px 수준의 터치 영역을 목표로 두고, 본문은 14~16px 범위에서 실제 가독성을 확인한다.

완료 조건: 360/390/430px와 데스크톱에서 조작 영역이 겹치지 않고, 상세창의 닫기·뒤로가기·포커스 복귀가 동작한다. 단순 간격 변경의 값 자체를 고정하는 테스트는 추가하지 않는다.

주요 재사용: [MonthNavigator.tsx](C:/Users/playz/cy/src/components/common/MonthNavigator.tsx), 프로젝트의 기존 공통 대화상자.

### 04 작업자 조회와 달력 및 목록 개선

선행 조건: 03. R02, R03, R04, R06, R07, R08, R14의 대체 조회를 구현한다.

- [ ] 조회월과 전체·재직·퇴사 선택을 모바일에서도 항상 보이게 한다.
- [ ] 최초 상태를 전체로 바꾸되 서버에서 허용한 팀 범위를 유지한다.
- [ ] 다른 팀·작업자·월로 이동할 때 선택 상태와 늦게 도착한 이전 조회 응답을 처리한다.

- [ ] 복수 현장은 모두 펼쳐 보여주고 빈 날짜에는 근무내역 없음 상태를 표시한다.
- [ ] 목록은 날짜·현장·공수·금액 중심으로 축약하고 세부 사항은 펼침으로 제공한다.
- [ ] 상세를 닫으면 선택월·작업자·스크롤을 유지한다.
- [ ] 독립 출력일보 메뉴 제거 전 대체 조회 경로가 동작하는 것을 확인한다.

완료 조건: 날짜·상태를 필터 없이 바꾸고 긴 현장명을 읽을 수 있다. 달력·목록·요약의 공수와 금액이 같은 원천에서 동일하게 계산된다. 재직·퇴사 조회가 로그인한 사용자의 접근 범위를 확대하지 않는다.

## 검증 명령과 적용 범위

실행 시점의 package.json과 스크립트를 다시 확인한다. 아래는 현재 프로젝트 명령을 기준으로 한 실행 형태다.

- 각 단계에서는 변경 범위의 테스트와 lint를 우선 실행하고, 새 수정·실패·미해결 문제가 없으면 같은 검사를 불필요하게 반복하지 않는다.
- lint는 현재 설치된 ESLint로 실제 변경 파일만 검사한다. 기존 lint:improvements 명령은 이번 대상 화면 전체를 포함하지 않으므로 이것만 실행하고 끝내지 않는다.
- 새 팀원 계정 승인에 필요한 서버·화면·규칙 테스트를 09에서 추가한다. 위 기존 명령 목록만으로 새 기능이 검증되는 것은 아니다.
- test:functions에서 emulator 전용 검사가 skipped이면 보안 검증 통과로 계산하지 않는다.
- account-access Rules 검증은 demo 프로젝트의 Auth·Firestore 에뮬레이터 설정을 갖춘 실행기에 연결한다. 운영 프로젝트를 테스트 대상으로 사용하지 않는다.
- 화면 간격 같은 단순 스타일 값에 맞춘 테스트를 남발하지 않는다. 월·팀·선택 상태, 데이터 정확성, 중복 처리, 권한 경계를 우선 검증한다.

## 작업 소유권과 완료 기록

기본 owner는 현재 작업의 통합 담당자 한 명이며, 위 단계를 순차 진행한다. 병렬 작업을 시작하는 경우 먼저 owner, allowed files, forbidden files, acceptance tests를 정하고 한 파일을 동시에 수정하지 않는다. 이 계획 자체는 병렬 에이전트 실행을 요청하지 않는다.

허용 수정 범위는 각 단계의 명시 파일, 직접 의존하는 서비스·컴포넌트와 관련 테스트다. 공유 컴포넌트, package manifest, lockfile, 배포 설정은 통합 owner만 수정한다. 승인 없이 작업 범위를 넓히지 않으며 기존 다른 작업의 수정 파일은 소유권을 확인한다. 전체 formatter, 무차별 restore, git reset --hard, git clean을 사용하지 않는다.

각 작업의 완료 기록은 작업 추적 도구나 실행 보고에 다음 항목을 남긴다. AGENTS.md나 장기 지식 문서에 현재 진행률을 넣지 않는다.

| 기록 항목 | 내용 |
| --- | --- |
| 작업과 요구사항 | 단계 번호, 관련 R 번호 |
| 변경 범위 | 실제 수정 파일과 사용자 동작의 변화 |
| 자동 검증 | 실행한 명령, 결과, 기존 실패와 신규 실패 구분 |
| 실제 화면 검증 | 역할, 화면 폭, 브라우저, 기기와 시나리오 |
| 데이터·권한 검증 | 합계 대조, 범위 밖 접근 차단 결과 |
| 남은 항목 | 미해결, 보류 이유, 미검증 환경 |
| 운영 상태 | 로컬 구현, 출시 후보, 배포, 운영 확인을 구분 |

완료 기준을 통과하지 못하면 다음 단계의 완료로 덮지 않고 현재 단계의 결함 또는 명시적인 미검증 항목으로 남긴다. 이 기획 요청만으로 운영 배포, 실제 계정 승인, 운영 메뉴·데이터 변경이나 외부 전송을 실행하지 않는다.
