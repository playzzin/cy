## 이번 변경

- 서버 운영 설정으로 전체 중지, 지정 계정 시범 운영, 전체 운영을 구분한다. 설정이 없거나 잘못되면 기능을 열지 않는다.
- 자동 보고 실행은 별도 스위치로 중지한다. 전체 기능이 열려 있으면 기존 보고서 다운로드와 예약 중지·삭제는 계속 사용할 수 있다.
- 대화·파일·예약의 현재 계정 상태, 운영 정책 버전과 기존 팀 권한을 함께 검사한다. 시범 운영 대상에 넣어도 기존 조회 권한은 확대되지 않는다.

- AI 설정 목록에 AI 업무 도우미 경로를 추가했다. 화면 스위치와 서버 운영 권한은 별개이며 서버 정책이 최종 기준이다.

- 출시 검사 스크립트와 읽기 전용 운영 점검 스크립트를 추가했다. 출시 지문에는 Git에 아직 추가하지 않은 앱·서버·스크립트 파일도 포함해 검사 중 코드 변경을 놓치지 않는다.

## 서버 운영 설정

권한 있는 운영 담당자가 `server_settings/ai_workspace` 문서의 `runtime` 필드를 설정한다. 일반 클라이언트가 이 문서를 직접 읽거나 쓰도록 허용하지 않는다. 이 작업에서는 운영 문서·권한·예약을 변경하지 않았다.

아래 값은 구조 예시다. 계정 UID는 별도 안전한 운영 경로에서 실제 승인 계정으로 지정하며 문서·로그에 복사하지 않는다.

```json
{
  "version": 1,
  "revision": 1,
  "mode": "pilot",
  "pilotUids": ["<approved-auth-uid>"],
  "schedulerEnabled": false
}
```

| 필드 | 의미 |
|---|---|
| `version` | 현재 구조 버전, 정수 1 |
| `revision` | 양의 정수. 접근 범위 지문에 포함되는 운영 정책 버전 |
| `mode` | `off`: 전체 차단, `pilot`: 지정 계정만 허용, `on`: 기존 역할·팀 정책을 만족하는 계정 허용 |
| `pilotUids` | 최대 20개. 관리자도 pilot 목록에 없으면 차단 |
| `schedulerEnabled` | 예약 저장·재개·재시도·자동 실행 허용 여부 |

정책 변경으로 과거 결과 접근과 기존 예약 승인을 무효화해야 할 때 `revision`을 증가시킨다. 기존 대화 결과·정기 보고 파일은 이전 지문으로 받을 수 없고, 예약은 다음 실행 때 권한 변경으로 중지되므로 사용자가 현재 조건으로 재확인·저장해야 한다. 단순 자동 실행 일시 중지·재개는 같은 revision에서 `schedulerEnabled`만 변경할 수 있다. 시범 명단·모드 변경은 즉시 현재 접근 검사에 반영된다.

## 운영 적용 순서

1. 출시 대상 변경과 계정별 역할·팀 범위를 검토하고, 결과 7일 보관·최대 5개 예약·5분 점검·함수 비용을 운영 기준으로 확정한다. 최신 소스로 로컬 출시 검사를 통과시킨다.
2. 확정된 인덱스 변경만 적용하고 모두 `READY`인지 확인한다. 필요한 컬렉션은 `ai_report_runs`, `ai_report_schedules`, `cardBillings`, `accommodation_billing_documents`, `vehicle_billing_documents`다. 다른 변경이 섞인 전체 인덱스 파일의 무검토 적용은 피한다.
3. 운영 설정이 없거나 `off`인 상태에서 선택한 세 함수만 배포하고 예약 인프라 생성을 확인한다. 코드에는 권한 검사가 필수이며, 시범 운영을 위해 Rules를 완화하지 않는다.
4. 출시 검사와 일치하는 UI 산출물을 배포한다. 읽기 전용 운영 점검으로 세 함수·인덱스·비인증 거절·예약 작업·Hosting 산출물을 확인한다. 자동 점검의 성공은 실제 로그인 검증의 대체물이 아니다.
5. 승인 계정만 `pilot`으로 열고 `schedulerEnabled: false`로 대화·검색·후속 질문·저장 분석·PDF·엑셀을 실제 계정에서 확인한다. 관리 역할, 팀 범위 역할, 비대상 계정 및 정지 계정의 기대 결과를 각각 확인한다.
6. 동일 기간·동일 기준의 기존 화면과 결과·파일 수치를 대조한다. 확정 정산 표본이 없다면 확정액 정확도 항목은 미검증으로 유지한다. 현재 일보 금액을 과거 확정 금액의 근거로 사용하지 않는다.
7. 시범 계정에 한해 자동 보고를 켜고 화면에서 시험 예약 내용을 확인·저장한다. 실제 Auth→callable→Scheduler→보관 결과→다운로드를 검증한다. 중복 호출·지연·권한 변경·실행 중 중지·실패·만료·재시도도 운영 로그와 이력으로 확인한다.
8. 오류율·처리/지연 시간·DB 읽기·파일 생성 메모리·비용을 관찰한 뒤 운영 범위를 확대한다. `on` 전환은 기존 업무 권한을 우회하지 않는다. 기획의 p95 목표와 비용 상한은 실제 부하에서 별도로 검증한다.

선택 함수 배포 대상은 `functions:aiWorkspace,functions:aiWorkspaceReports,functions:generateScheduledWorkspaceReports`다. 실제 배포 명령은 출시 소스·인덱스·산출물 검토 후 실행하며 이번 작업에서는 실행하지 않았다. 예약 함수의 생성·중복 실행 특성은 [Firebase 1세대 예약 함수 문서](https://firebase.google.com/docs/functions/1st-gen/schedule-functions-1st)를 따른다.

## 중지·복구

- 자동 보고만 멈추기: `schedulerEnabled: false`. 새 예약·재시도·자동 생성을 차단한다. 이전 예약과 예정 시간은 보존하고, 실행 중이던 회차의 늦은 결과를 보관하지 않는다. 이때 정기 보고 목록·기존 결과 다운로드·개인 예약 중지·삭제는 사용할 수 있다.
- 전체 기능 멈추기: `mode: off`. 분석·저장 목록·결과 다운로드를 포함해 모두 차단한다. 원본 업무 데이터는 변경하지 않는다.
- 만료 정리: 서버 스위치를 꺼도 예약 함수의 만료 삭제는 계속된다. Cloud Scheduler 작업 자체를 중지하면 물리 삭제도 멈추므로 정상 중지에는 서버 스위치를 먼저 사용한다. 파일 접근의 만료 검사는 별도로 유지된다.
- 복구: 원인을 해결하고 현재 코드·인덱스·운영 설정을 점검한 뒤 시범 계정부터 연다. 실패 회차는 조건·권한·보관 기한이 유효한 경우에만 최대 3회 범위 안에서 수동 재시도한다. 다음 정기 일정은 별도로 유지된다. 밀린 회차 전체를 일괄 생성하지 않는다.
- 관찰: `ai-workspace`, `ai-workspace-saved`, `ai-workspace-report`, `ai-workspace-report-claim-failed` 로그의 상태·처리 시간·지연을 본다. 질문·키·원장 원문을 추가로 로깅하지 않는다. 별도 자동 경보나 비용 강제 차단은 이번에 설치하지 않았다.

## 남은 출시 조건

운영 배포, 실제 역할 계정의 전 과정, 확정 금액 대조, 실제 Cloud Scheduler 실행, 운영 부하·비용·장기 만료 관찰이 남아 있다. 코드상 제한과 합성 자료 시험은 이 항목들의 운영 검증 완료를 뜻하지 않는다. Git commit·push, 운영 데이터 변경, 외부 이메일·메신저 발송도 수행하지 않았다.
