# 매입매출 거래대장 점검 — 2026-09-29

대상: `http://localhost:3000/payroll/workbook-ledger`

이번 작업은 점검이다. 애플리케이션 소스와 실제 장부 데이터를 수정하지 않았다. 아래 금액과 거래 식별자는 모두 검증용 합성 데이터다.

## 점검 결과

계산·가져오기·저장 실패 처리에서 7개 문제를 로컬 재현했다. 추가로 실제 변경 작업을 수행하지 않고 확인한 코드상 위험 3개가 있다. 기존 테스트가 통과하더라도 이 경계 사례들은 방어되지 않는다.

P1은 금액 또는 데이터 정합성에 직접 영향을 주어 우선 수정할 항목, P2는 특정 입력·조회 조건에서 발생하는 오류다.

### 1. P1 — 선수금 사용을 실제 입금으로 다시 차감한다

- 근거: `src/pages/taxinvoice/WorkbookLedgerModel.ts:1929`, 특히 1941–1943행.
- `buildLedgerRows`가 `sourceType: 'advanceUsage'`인 내부 대체 행을 일반 입금과 동일하게 차감한다.
- 재현: 첫 거래 110,000원, 실제 입금 160,000원, 두 번째 거래 55,000원, 첫 거래의 선수금 50,000원을 두 번째 거래에 사용.
- 기대: 실제 거래와 입금의 차액은 5,000원이다.
- 실제: 거래장 잔액은 -45,000원, 전체 조회의 미수금은 5,000원으로 서로 다르다.
- 개선: 현금 입출금과 선수금 배분을 구분하고, 거래장·조회·엑셀·인쇄에 같은 계산 정책을 적용한다. 배분 이력을 표시하더라도 현금 합계에는 중복 반영하지 않아야 한다.

### 2. P1 — 취소 거래를 원래 거래와 중복으로 판단한다

- 근거: `src/pages/taxinvoice/WorkbookLedgerModel.ts:1240`, 특히 1247–1248행.
- 중복 판별 키를 만들 때 금액에 `Math.abs`를 적용해 부호가 사라진다.
- 재현: 구분·날짜·거래처·현장이 같은 +110,000원 거래가 이미 있고 -110,000원 취소 거래를 업로드한다.
- 기대: 취소 거래 1건을 신규로 가져와야 한다.
- 실제: 신규 0건, 중복 1건으로 제외된다.
- 개선: 금액 부호와 원본 문서 식별자를 보존한다. 동일 날짜·금액이더라도 서로 다른 거래일 수 있으므로 중복 의심 행의 검토·선택 경로도 필요하다.

### 3. P1 — DB 다운로드 파일로 복원하면 입금 연결이 끊어진다

- 근거: `src/pages/taxinvoice/WorkbookLedgerModel.ts:441`, `:856`, `:1065`; `src/services/workbookLedgerService.ts:412`.
- DB 내보내기는 `matchedEntryId`를 포함하지만 원본 행의 `id`는 포함하지 않는다. 다시 가져올 때 원본 거래에는 새 ID가 생성되고, 입금은 이전 ID를 계속 참조한다.
- 재현: 매출 110,000원과 연결 입금 110,000원을 `toDbRow → parseImportedDbEntries → 새 ID 부여` 흐름으로 왕복시켰다.
- 기대: 완납 상태, 미수금 0원 유지.
- 실제: 연결된 원본을 찾지 못해 미수금이 110,000원으로 돌아온다.
- 추가 누락: 내보내기 형식에서 `sourceType`, `sourceId`, `manDays`도 보존되지 않는다.
- 개선: 백업·복원용 형식에 식별자와 출처 정보를 포함하고, 가져오기 과정에서 원본 ID와 새 ID 간 연결을 재작성한다. 단순 추가 업로드와 복원 기능을 UI에서 구분해야 한다.
- 검증 한계: 실제 다운로드 파일 저장이나 실제 DB 복원은 수행하지 않았다. 현재 내보내기·가져오기 함수와 서비스의 ID 생성 규칙을 사용한 로컬 재현이다.

### 4. P1 — 대량 등록 일부 실패 시 저장 결과와 로그가 불완전하다

- 근거: `src/services/workbookLedgerService.ts:401`, 특히 407–439행.
- 400건씩 순차 저장하고, 모든 묶음이 성공한 뒤에만 캐시를 지우고 변경 로그를 기록한다.
- 재현: Firestore를 메모리 모의 구현으로 대체해 401건 등록 중 두 번째 묶음만 실패시켰다.
- 실제: 400건은 저장되었지만 호출은 실패하며 변경 로그는 0건이다. 먼저 읽어 둔 빈 캐시도 유지되어 후속 조회가 0건을 반환했다.
- 영향: 사용자는 일부 저장 사실을 알 수 없고, 입력폼 재등록처럼 새 ID를 만드는 경로로 재시도하면 중복 위험이 있다. 엑셀 업로드에는 별도 중복 검사가 있으므로 모든 재시도가 곧 중복으로 이어진다고 볼 수는 없다.
- 개선: 성공·실패 건수를 분리해 반환하고, 성공한 묶음의 로그와 캐시를 즉시 처리한다. 재시도 시 같은 작업을 중복 저장하지 않는 식별자도 필요하다.

### 5. P1 — 음수 입금액이 검수를 통과한 뒤 저장에서 사라질 수 있다

- 근거: `src/pages/taxinvoice/WorkbookLedgerModel.ts:1205`; `src/pages/taxinvoice/WorkbookLedgerPage.tsx:982`.
- 재현: 공급가액 100,000원, 입금금액 -50,000원을 입력 검증 함수에 전달.
- 기대: 음수 입금이 지원되지 않는다면 저장 전에 오류로 안내해야 한다.
- 실제: 검증 오류 배열이 비어 있다. 이후 저장은 `paymentAmount > 0`인 경우에만 입금 행을 생성하므로 음수 입금은 저장되지 않는다.
- 개선: 입력폼·DB 수정·업로드가 동일한 검증을 사용해야 한다. 환불을 허용할지 별도 거래 유형으로 처리할지도 명확히 해야 한다.
- 검증 수준: 검증 통과는 로컬 실행으로 재현했고, 저장 시 누락은 현재 저장 분기를 추적해 확인했다. 실제 저장하지 않았다.

### 6. P2 — 적용월 13이 정상 입력으로 통과하고 부가세 조회에서 누락된다

- 원인: 적용월의 1–12 정수 검사가 없고, 보고서는 유효한 분기가 없는 행을 경고 생성 전에 제외한다.
- 개선: 입력과 서비스에서 범위를 검증하고, 기존 잘못된 데이터는 별도의 오류 목록으로 보여 준다.

### 7. P2 — 미래 취소 거래가 현재 미수금을 미리 줄인다

- 근거: `src/pages/taxinvoice/WorkbookLedgerModel.ts:1988`, `:2311`.

## 코드상 추가 위험 — 파괴적 동작은 재현하지 않음

### A. 최근 일부 데이터만으로 연결 거래의 수정·삭제를 허용할 수 있음

- DB 기본 조회는 최근 300개 문서다 (`WorkbookLedgerModel.ts:279`, `:325`).
- 단일 수정·삭제와 일괄 삭제의 연결 관계 검사는 현재 `entries`만 확인한다 (`WorkbookLedgerPage.tsx:1518`, `:1728`, `:1832`).
- 연결된 입금이나 선수금 사용이 조회 범위 밖에 있으면 원본 보호가 빠질 수 있다.
- 서비스의 삭제 함수도 연결 관계를 다시 조회하지 않는다 (`workbookLedgerService.ts:461`).
- 개선: 수정·삭제 직전에 서버에서 전체 연결 관계를 확인하고 동시 변경까지 보호한다. 실제 삭제는 수행하지 않았다.

### B. 정산 검증 실패 뒤 미검증 미리보기가 정상 결과로 사용될 수 있음

- 기간 미리보기 결과를 먼저 반영한 다음 전체 이력을 검증한다 (`WorkbookLedgerPage.tsx:310`).
- 전체 이력 조회가 실패해도 미리보기 데이터를 유지하고 `finally`에서 검증 중 상태를 해제한다 (`:364–373`).
- 다운로드 및 정산 버튼은 주로 검증 중 여부로 비활성화되므로 실패 후에는 미검증 결과 사용 가능성이 있다.
- 개선: 검증 대기·성공·실패를 구분하고, 실패 상태에서 정산·내보내기를 제한하며 재시도 경로를 제공한다.
- 검증 한계: 실제 네트워크를 차단해 브라우저에서 재현하지 않았다.

### C. 첫 입력폼 진입 시 자동완성 목록이 갱신되지 않는 구조

- 초기 진입은 카탈로그만 읽는다 (`WorkbookLedgerPage.tsx:383`).
- 회사·현장·팀을 참조 변수에 넣은 후, 화면 목록을 갱신하는 `rebuildLookupOptions`는 장부 조회 결과가 있을 때만 실행한다 (`:343–362`).
- 따라서 첫 입력폼 진입에서는 목록이 비어 있고 다른 탭 조회 후에야 채워질 수 있다.
- 개선: 카탈로그 조회 완료 시 장부 데이터 유무와 무관하게 자동완성 목록을 갱신한다.
- 검증 한계: 별도 신규 브라우저 세션에서 전후 목록을 비교하지 않았다.

## 화면·사용성 개선

1. DB 탭에 ‘최근 일부 조회 중’을 더 뚜렷하게 표시하고, 필터가 전체 DB에 적용되는지 설명한다. ‘전체 DB 보기’는 현재 미매핑 필터 해제만 수행하므로 실제 전체 로딩 버튼과 이름을 구분한다.
2. 거래장 잔액이 기간 내 증감인지 이월 포함 잔액인지 명시한다. 현재 `buildLedgerRows`는 기간 시작 잔액을 0으로 계산한다.
3. DB 초기화 같은 위험 작업을 일반 다운로드·검색 도구와 분리하고, 소프트 삭제 내역의 복원 경로를 제공한다.
4. 저장·검증·네트워크 오류를 행 단위 또는 화면 내 상태로 유지한다. 실패 알림을 닫은 뒤에도 미검증 상태가 보여야 한다.
5. 입력, DB 편집, 정산, 분기 보고서, 내보내기를 분리해 관리하고 공통 계산·검증을 재사용한다. 현재 페이지는 7천 행 이상이며 화면 간 계산 불일치가 생기기 쉽다.
6. 위 7개 재현 사례를 회귀 테스트에 추가하고, 연결 거래 수정·삭제 및 부분 저장 실패까지 통합 검증한다.

## 검증 기록과 한계

- 실제 Chrome에서 입력폼, DB, 거래장, 전체 조회, 분기 부가세 진입을 확인했다. 마지막에는 원래 입력폼으로 돌아왔고 작성 0건 상태를 확인했다.
- 점검 초기에 공통 `App.tsx:105`의 `CardStatementDetailsPage` 모듈 누락으로 개발 오류 화면이 나타났다. 첫 타입 검사도 같은 오류로 실패했다. 점검 도중 외부 작업으로 해당 파일이 생성되었고, 이후 브라우저에서는 오류 오버레이가 사라졌다. 이 점검에서 그 파일을 만들거나 수정하지 않았다.
- 거래대장 관련 기존 7개 테스트 파일, 총 49개 테스트 통과.
- 관련 페이지·모델·입력 컴포넌트·서비스·미수금 유틸리티 5개 파일의 ESLint 검사 통과.
- 파일 추가 후 전체 타입 검사를 다시 실행했지만 `src/pages/support/CardStatementDetailsPage.test.tsx:61`에서 TS2769로 실패했다. `ByRoleOptions`에 지원되지 않는 `exact` 옵션이 전달된 오류다. 거래대장 경로 외의 오류이며 전체 프로젝트 타입 검증은 통과하지 않았다.
- 계산 및 가져오기 경계 사례는 현재 TypeScript 코드를 실행해 검증했다. 부분 저장 실패는 실제 Firebase 연결 없이 모의 저장소에서 실행했다.
- 실제 DB 등록·수정·삭제, AI 문서 업로드, 지급 처리, 데이터 내보내기 파일 다운로드, 배포는 수행하지 않았다.
- 모바일 화면, 실제 저장 후 재접속, 인쇄·캡처 결과, 운영 배포본, 권한별 접근은 검증하지 않았다. 운영용 빌드도 이번 읽기 중심 점검 범위에 포함하지 않았다.
