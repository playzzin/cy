## BLOCK 근거 3건

### B1. signed `-50` 부호 변경

저장값이 음수 공제/환급(`-50`)일 때:

| 위치 | 변환 | 결과 |
|---|---|---|
| 화면/print `PayslipTemplate.tsx` 37–41, 471–478, 792 | `amount < 0` → `+${Math.abs}원` | 표시가 양수 환급 문자열로 바뀜 |
| 미연결 print `PayslipExcelPrintTemplate.tsx` 12–16, 574–628 | 동일 | 동일 |
| XLSX 라인 `payslipWorkbook.ts` 75, 81, 91 | `-Math.abs(amount)` | 음수 환급도 차감(음수)로 강제. 화면과 **불일치** |
| XLSX 총차감 251, 258 | `-Math.abs` / footer `Math.abs` | 부호 제거 |
| XLSX formula 515–517 | `F+H` where H is forced negative; cache `Math.abs(totalDeduction)` | `totalDeduction=-50`이면 실지급이 `gross-50`으로 재계산될 수 있음. 저장 net(`gross-(-50)`)과 **불일치** |
| 화면 합계 `PayslipTemplate.tsx` 201–206 | `Math.max(0, … - taxTotal)` | 보험/원천/사업 세후를 0 하한 |

서버 materializer 테스트는 `-50` 보존을 요구한다 (`functions/src/monthlyPayslipArtifactIssue.test.ts` 373–378, client factory `monthlyPayslipArtifact.test.ts` 405–411). **출력 경로가 그 보존을 깨므로 3/3 수용 불가.**

### B2. missing / malformed artifact 시 live fallback

- UI는 `monthlyPayslipArtifact`를 import하지 않는다. 발행본 부재 = **항상 live/정산 경로**. 이것이 fallback이다.
- 정산 ② malformed는 fail-closed (`monthlyPayrollSnapshot.ts` 352–353, 370, page 2402–2414, 6004–6008). **payslip artifact 부재에는 이 가드가 없다.**
- `canUseLiveMonthlyPayrollLedgerFallback` 57–62는 **가불대장** 전용. 미확정 월 live 허용. payslip 3/3에 재사용하면 미발행 월이 live 명세서를 낸다.
- `openPayslipPreview` 3367–3375는 토글 켜진 채 모달을 열면 live 공제를 다시 넣는다.
- 3/3 checklist: “미발행·로딩·오류를 빈 명세서로 표시하지 않음” ([[2026-09-02 P0-1 급여명세서 서버 발행 무결성 조사]]). 현재는 반대로 live를 보여 준다 → **BLOCK**.

### B3. snapshot-only 행에서 worker / search / model filter

정산 ② 행: worker·search·team은 적용됨 (2364–2376, 378–380). **완전히 유지된다고 쓰면 안 된다.**

- search: live는 `workerNameSearch` NFC/공백 제거, snapshot include는 `toLowerCase().includes` → 공백·정규화 불일치 **BLOCK**
- salary model: payslip 목록에 미적용. 3/3이 “기존 model filter 유지”를 요구하면 현재 구현에 유지할 필터가 없다. renderSnapshot에 `id` 없음
- team: include는 `teamId`. renderSnapshot은 `teamName`만. snapshot-only 이식 시 팀 필터 **BLOCK**

### 1) sourcePaymentId(rowKey) split/parse — **BLOCK**

구조적으로 4-tuple인 **검증된 정산 row**만 보면 `split('__')`는 한 가지로 떨어진다.

- 서버 정산 validator는 `expectedKey = yearMonth + '__' + teamId + '__' + workerId + '__' + salaryModel` (비인코딩 접합). `functions/src/monthlyPayrollStatusTransition.ts` 222–224, 클라이언트 미러 `src/services/monthlyPayrollSnapshotValidation.ts` 228–229
- 각 구성 요소는 `canonicalComponent`: nonblank이고 `__` 금지. 같은 파일 33, 181, 211, 223–224
- `__`가 workerId에 들어가면 5-tuple이 되고 validator가 거부한다. `monthlyPayrollStatusTransition.test.ts` 178–183
- 서버 issue의 `canonicalRowKey`도 정확히 4 part. `monthlyPayslipArtifactIssue.ts` 122–128, 133

그래도 목록 필터 키를 여기서 파면 안 되는 이유:

| 함정 | file:line | 왜 깨지나 |
|---|---|---|
| factory `sourcePaymentId`는 opaque | `monthlyPayslipArtifact.ts` 243–245, 296–305. fixture `monthlyPayslipArtifact.test.ts` 53 `payment.a/b` | 4-tuple이 아니다. part count fallback이 생긴다 |
| rowKey는 비인코딩, artifactId·settlementId는 인코딩 | issue 103–114, 225–228, factory 291–305. fixture rowKey `2026-08__team.a/b__worker.a/b__monthly`, settlementId `2026-08__team%2Ea%2Fb` | `.` `/` `_`를 한 parser로 다루면 team과 encoding이 섞인다 |
| `_` → `%5F`, `.` → `%2E`는 artifactId 전용 | factory 291–293. issue 테스트 artifactId가 `%5F%5F`로 rowKey의 `__`를 재인코딩 | artifactId를 다시 split/decode하면 nested encoding. 필터 키가 아님 |
| `/`는 row 구성 요소에 허용, opaque id에는 금지 | issue fixture `team.a/b`, `worker.a/b`. `canonicalOpaqueId` 120–121은 `/` 거부 | 구성 요소 규칙을 ID 종류마다 다름 |

| 접미사 기본값 monthly | `resolveKBSalaryFilterFromPaymentId` 56, `matchesMonthlyAdvanceLedgerSalaryModelFilter` 179–183 | 파싱 실패를 monthly로 삼키는 경로가 이미 있다 |

**금지할 parser fallback**

- `sourcePaymentId` / `payment.id` / `rowKey`를 `split('__')`·`lastIndexOf('__')`·정규식으로 분해해 team/model을 씀
- part 수가 4가 아니면 decodeURIComponent 후 재split, 앞/뒤 토큰 greedy 매칭, `endsWith('__월급제')` 등 suffix로 복구

- `sourceSettlementId` 2-tuple decode로 `sourceTeamId`를 대체 (인코딩 규칙이 다르고 salaryModel이 없음)
- 필드 부재 시 salaryModel을 `monthly`로 기본 지정

### 4) canonical vs exact saved teamId — 발행 시 **exact saved 보존**

- live 목록은 **조회 시점**에 `resolveCanonicalTeamId` (page 1931–1938, 2360, 2372). resolver는 저장 `item.teamId`를 canonicalize한 뒤 selected scope와 비교 (306–316, 343–349)
- snapshot 테스트는 저장값이 `legacy-team-A`인 행을 그대로 두고, 필터만 canonical `team-A`로 맞춘다 (482–516)
- 발행 때 canonical로 바꾸면 (1) 정산 문서 ID와 불일치, (2) 이후 alias 맵 변경 시 발행본이 당시 저장 ID를 잃음, (3) 서버가 쓸 공인 함수가 없음

권고: envelope `sourceTeamId` = **저장된 그대로**. 목록 비교는 live와 같이 `canonicalizeTeamId(sourceTeamId) === selectedCanonical`. canonical을 발행 필드에 이중 저장하지 않음.

`normalizePersistedTeamId`가 비우는 센티널 (`no-team`, `__no_team__`, `unresolved:`, page 1899–1903)은 정산 validator의 `canonicalComponent`를 통과할 수 없다. 그런 행은 발행 전 정산 검증에서 이미 fail-closed.
