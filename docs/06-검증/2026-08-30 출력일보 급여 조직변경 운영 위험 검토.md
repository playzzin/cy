# 2026-08-30 출력일보·급여·조직변경 운영 위험 검토

- 검토일: 2026-08-30
- 범위: 출력일보, 공수 집계, 급여·가불·정산, 작업자 팀 이동, 현장 변경·삭제, 관련 권한
- 방식: 운영 데이터 무변경 정적 코드 검토 + 관련 테스트 실행
- 상태: 1차 검토. 실제 운영 데이터에서 발생 건수는 아직 집계하지 않음
- 최상위 기준: `../../개발지침.md`

## 결론

현재 가장 큰 위험은 **원본 문서는 저장됐지만 파생 집계가 어긋나는 문제**, **과거 귀속 이력 없이 현재 팀·현장 값만 바꾸는 문제**, **삭제·덮어쓰기 중 실패하면 일부 데이터만 남는 문제**다.

운영 중에는 다음 조치를 우선 적용한다.

1. 출력일보 대량 덮어쓰기 전 대상 일자를 백업하고 건수·공수 합계를 기록한다.
2. 작업자·팀·현장은 삭제하지 말고 퇴사·종료·비활성 상태로 전환한다.
3. 팀 이동과 현장 변경은 효력일 및 변경 전후 값을 별도로 기록한다.
4. 확정 급여의 원천 일보를 수정하면 자동 반영된다고 가정하지 말고 차이 검토 후 정정본을 발행한다.
5. 가불 원장이 여러 건이면 최신 확정 정정본을 사람이 확인한다.
6. 대용량 Excel 출력일보 업로드는 신규 작업자·신규 팀·신규 현장이 없는 자료만 사용하고 업로드 후 급여 포함 여부를 대조한다.

## 독립 병렬 감사에서 추가 확인된 중요 결함

### A. 조회 실패 후 이전 날짜 화면을 새 날짜에 저장할 수 있음 — Critical

- `DailyReportGridInput`은 날짜를 먼저 바꾸고 새 날짜 조회가 실패해도 이전 `ledgers`를 비우지 않으며 저장을 잠그지 않는다.
- 저장 버튼은 `loadErrorMessage`와 `fetching`을 차단 조건으로 사용하지 않는다.
- 재현 가능 흐름: A일 조회 → B일 이동 → B일 조회 실패 → 전체 저장 → A일 화면 내용으로 B일 자료 삭제·재생성.
- 위치: `DailyReportGridInput.tsx:791-823, 1066-1113, 2081-2085, 2161-2163, 2642`

**즉시 통제:** 조회 오류가 한 번이라도 표시되면 그 화면에서 저장하지 말고 새로고침 후 대상 날짜·건수·합계를 다시 확인한다.

### B. `reviewed` 급여의 화면과 실제 확정 snapshot이 달라질 수 있음 — Critical

- `reviewed`부터 저장본 수정은 잠기지만 화면 snapshot 고정은 `confirmed|paid`에만 적용된다.
- 검토완료 후 일보·단가·가불을 바꾸면 화면은 최신 원천으로 재계산되지만 `reviewed→confirmed`는 과거 저장 행을 그대로 확정한다.
- 확정 직전 화면 금액과 실제 확정된 금액이 다르고, 새로고침 후 금액이 되돌아갈 수 있다.
- 위치: `monthlyPayrollSettlementService.ts:197-200, 252-263, 303-339`, `MonthlyWageDraftPage.tsx:2294-2332`

**즉시 통제:** `reviewed` 상태는 사용하지 말고 모든 원천 변경 완료 후 초안 재저장·대조·즉시 확정한다.

### C. 음수 공제·상계액 저장 시 부호가 소실될 수 있음 — High

- 화면과 명세서는 음수 조정을 표시하지만 정산 저장 시 `personalDeduction`과 `totalDeduction`을 `Math.max(0, ...)`로 절단한다.
- 공제 breakdown과 실지급액은 음수 조정이 반영된 채 snapshot에 남아 서로 불일치할 수 있다.
- 위치: `MonthlyWageDraftPage.tsx:1586-1620, 5263-5280`, `PayslipTemplate.tsx:461-489`

**즉시 통제:** 음수 상계가 포함된 급여는 확정하지 말고 총공제·실지급·breakdown 세 값을 별도 대조한다.

### D. 확정 후 팀·급여형태 변경 시 구 확정 행과 신 원천 행이 함께 나타날 수 있음 — High

- 급여 행 ID가 `월+작업자+팀+급여형태`로 구성된다.
- 확정 후 팀 ID·별칭·급여형태를 바꾸면 현재 원천 ID와 확정 snapshot ID가 달라져 두 행이 모두 목록에 추가될 수 있다.
- 위치: `usePayrollData.ts:560-563, 615-617`, `MonthlyWageDraftPage.tsx:2328-2350`

**즉시 통제:** 확정월의 팀·급여형태·workerId는 직접 수정하지 않고 정정 승인 및 중복검사 후 처리한다.

### E. 한 작업자 행의 현장 변경이 같은 일보 전체 작업자를 이동시킬 수 있음 — High

- 목록 UI는 작업자 행 단위 수정처럼 보이지만 현장 변경은 report-level `siteId/siteName` 갱신으로 처리된다.
- 같은 일보 문서에 포함된 다른 작업자도 함께 다른 현장으로 이동한다.
- 위치: `DailyReportListV2.tsx:2111-2119, 2342-2348`, `dailyReportService.ts:1043-1085`

### F. 새 현장과 외부계정 접근범위가 자동 동기화되지 않음 — High

- 회사 계정 승인 시점 현장만 `account_links.siteIds`와 `users.linkedSiteIds`에 복제한다.
- 이후 같은 회사에 새 현장을 만들어도 기존 계정에 자동 추가하지 않는다.
- 위치: `functions/src/accountAccess.ts:303-311, 404-436`, `siteService.addSite`

### G. 권한 강등 직후 옛 custom claims가 잠시 유지될 수 있음 — High

- Rules는 사용자 문서 권한과 토큰 claims를 OR로 인정한다.
- 사용자 문서 transaction 후 claims를 갱신하므로 경쟁조건에서 옛 관리자 claims가 남을 수 있다.
- 일부 연결·해제 함수는 claims 갱신 실패를 경고만 하고 성공을 반환한다.
- 위치: `firestore.rules:105-147`, `functions/src/accountAccess.ts:457-469, 501-555, 718-729`

### H. 신고현장 조회 실패 후 수정·저장이 계속 허용됨 — High

- 조회 오류를 빈 배열로 바꾸고 저장·삭제 기능을 비활성화하지 않는다.
- 기존 값이 없는 것으로 오인해 신규 값으로 덮거나 삭제를 누락할 수 있다.
- 위치: `LaborCheckPage.tsx:239-255, 431-498`

### I. Excel 내보내기 파일과 다시 가져오기 형식이 호환되지 않음 — Medium

- 내보내기는 한글 열 이름을 만들지만 가져오기는 영문 raw field를 읽는다.
- 시스템 내보내기 파일을 복구 파일로 믿고 그대로 가져오면 행이 누락될 수 있다.
- 위치: `dailyReportTransferService.ts:221-266, 359-379`

## P0 — 즉시 운영 통제가 필요한 위험

### 1. 출력일보 덮어쓰기가 삭제 후 신규 저장 순서다

- 위치: `src/services/dailyReportService.ts:335-350`
- 기존 일보를 먼저 삭제하고 통계 차감·알림을 처리한 뒤 신규 일보를 저장한다.
- 신규 저장이 권한, 네트워크, 검증, Firestore batch 제한으로 실패하면 기존 일보만 삭제된 상태가 될 수 있다.
- 호출 화면: `FieldSchedulePlannerPage.tsx`, `DailyReportGridInput.tsx`, `DailyReportDragDropPage.tsx`
- 신규 batch 저장은 `dailyReportFirestoreService.ts:180-194`에서 500건 단위 분할 없이 단일 batch를 사용한다.

**운영 영향:** 해당 날짜·팀의 출력일보 유실, 공수·급여 누락, 누계 불일치.

**조치:** 삭제와 신규본 준비를 분리하고, 서버 transaction/세대 ID 방식으로 신규본 검증 완료 후 활성본을 전환한다. 그 전에는 덮어쓰기 전 건수·공수·금액 snapshot을 남긴다.

### 2. 대용량 Excel 업로드의 미등록 작업자는 급여에서 사라질 수 있다

- 위치: `src/pages/report/MassDailyReportUploader.tsx:200-220`
- 이름으로 작업자를 찾지 못하면 작업자 마스터를 만들지 않고 `batch_...` 임시 ID를 일보에 저장한다.
- 급여 집계는 `src/pages/payroll/hooks/usePayrollData.ts:504-508`에서 작업자 마스터를 찾지 못하면 그 일보 행을 건너뛴다.
- 같은 이름의 작업자가 여러 팀에 있으면 이름 하나만 key로 사용하는 `workerMap` 때문에 다른 작업자와 연결될 수 있다.

**운영 영향:** 출력일보에는 공수가 보이지만 월 급여에서는 누락되거나 다른 동명이인의 급여로 귀속될 수 있다.

**조치:** 미등록 작업자가 한 명이라도 있으면 업로드를 중단한다. 작업자 ID+팀 ID를 명시적으로 매핑하고 업로드 후 `일보 공수 합계 = 급여 원천 공수 합계`를 대조한다.

### 3. 작업자·팀·현장 영구 삭제에 참조 보호가 없다

- 작업자: `manpowerService.ts:240-275`
- 팀: `teamService.ts:127-136`
- 현장: `siteService.ts:104-115`
- 관리 화면은 참조 중인 일보·급여·가불·계정·현장 배정 존재 여부를 확인하지 않고 삭제를 실행한다.
- 여러 건 삭제는 `Promise.all`이므로 일부 삭제 후 한 건이 실패할 수 있다.
- 작업자 삭제 시 과거 일보는 남더라도 급여 집계가 작업자 마스터 부재로 해당 행을 건너뛸 수 있다.

**운영 영향:** 과거 급여 누락, 고아 참조, 현장/팀 조회 실패, 계정 연결 불일치.

**조치:** 영구 삭제 UI를 잠그고 `퇴사`, `종료`, `비활성` 상태만 사용한다. 삭제는 참조 0건과 별도 백업이 확인된 관리자 복구 절차에서만 허용한다.

## P1 — 높은 금액·귀속 오류 위험

### 4. 팀 이동에 효력일과 소속 이력이 없다

- 작업자 마스터의 현재 `teamId/teamName`만 변경하며 팀 이동의 시작일·종료일 이력이 없다.
- `TeamDatabase.tsx:265-299`는 작업자 문서와 팀 문서를 순차로 갱신한다.
- 중간 실패 시 작업자는 새 팀인데 팀의 `memberIds`에는 없거나, 반대로 양쪽 팀에 남을 수 있다.
- 과거 일보의 작업자 팀 snapshot이 없는 레거시 행은 일보 작성팀 또는 현재 작업자 팀으로 보완될 수 있다.

**운영 영향:** 이동월 급여가 이전 팀/신규 팀에 중복 또는 오귀속되고, 외부지원 비용과 팀 실적이 달라질 수 있다.

**조치:** `worker_team_assignments` 형태의 효력일 이력을 도입한다. 이동일 기준으로 이전 배정 종료와 신규 배정 시작을 하나의 서버 transaction으로 처리한다.

### 5. 현장 담당팀 변경도 다중 문서가 원자적으로 바뀌지 않는다

- `TeamDatabase.tsx:228-262`는 먼저 여러 현장의 담당팀을 변경한 뒤 팀의 `siteIds/siteNames`를 갱신한다.
- 실패하면 현장과 팀 문서가 서로 다른 상태가 된다.
- `siteService.updateSite`는 현장명 변경 때 작업자 이름 snapshot만 best-effort로 동기화하며 회사의 `siteIds/siteNames`, 계정의 `linkedSiteIds` 등 전체 참조를 함께 갱신하지 않는다.

**운영 영향:** 현장 목록 누락·중복, 담당팀 통계 오귀속, 발주사/임대사 포털 접근 거부 또는 과다 노출 가능성.

**조치:** 현장 담당 변경을 서버 원자 작업으로 만들고 변경 전후 참조 목록을 검증한다. 접근계정 영향 목록을 사전 출력한다.

### 6. 가불 정정본 선택이 최신본보다 절대금액 큰 과거본을 우선한다

- 위치: `src/pages/payroll/utils/advanceLedgerInput.ts:79-100`
- 후보가 여러 개면 `updatedAt`보다 금액 절대값 합계가 큰 원장을 먼저 선택한다.
- 과거 고액 원장을 0원 또는 저액으로 정정해도 과거 고액본이 계속 선택될 수 있다.
- 팀 정보 없는 레거시 원장은 각 팀 급여 행의 fallback 후보가 되므로 이동월의 여러 급여 행에 같은 원장이 연결될 가능성이 있다.

**운영 영향:** 실지급액 과소 계산, 동일 가불 중복 차감.

**조치:** `확정 상태 → 개정번호 → updatedAt` 순서로 최신 정정본 하나만 선택한다. 팀 없는 원장은 자동 적용하지 않고 수동 귀속 대기열로 보낸다.

### 7. 급여 초안은 동시 편집 시 마지막 저장이 이긴다

- `monthlyPayrollSettlementService.saveSettlements`는 기존 상태를 읽은 뒤 별도 batch로 draft를 저장한다.
- draft→draft 갱신에는 revision/사전조건이 없어 두 명이 동시에 편집하면 늦게 저장한 화면이 먼저 저장한 수정사항을 덮을 수 있다.
- 확정본 잠금과 상태 transaction은 존재하지만 초안 동시 편집 잠금은 없다.

**운영 영향:** 수동 가불·공제·메모가 조용히 사라질 수 있다.

**조치:** revision 번호와 `updatedAt` 비교를 적용하고 충돌 시 저장을 거부한다. 급여팀은 월·팀 단위 담당자를 한 명으로 제한한다.

### 8. 과거 출력일보의 급여형태를 현재 작업자 값으로 일괄 변경할 수 있다

- 위치: `dailyReportService.syncReportsSalaryModel:759-823`
- 현재 작업자 마스터를 기준으로 모든 과거 일보의 급여형태를 수정한다.
- 화면 호출 위치: `TotalPersonnelHistoryPage.tsx:902`

**운영 영향:** 과거 월급제/일급제/용역팀 분류와 세금·명세서 분리가 변경될 수 있다.

**조치:** 과거 확정월은 수정 금지하고, 미확정 기간과 명시적으로 선택한 행만 dry-run 차이 확인 후 수정한다.

## P2 — 누계·조회·감사 오류 위험

### 9. 출력일보 원본 저장과 누계 갱신이 분리되어 있다

- 일보를 먼저 저장한 뒤 작업자·팀·현장·회사 `totalManDay` 누계를 갱신한다.
- 누계 갱신 실패는 `Promise.allSettled` 경고만 남기고 일보 저장 성공을 유지한다 (`dailyReportService.ts:481-596`).

**운영 영향:** 출력일보 합계와 대시보드 누계가 달라진다.

**조치:** 누계를 기준 데이터로 사용하지 말고 일보에서 재집계한다. 정기 무결성 검사와 누계 재구축 작업을 제공한다.

### 10. 같은 날짜·팀·현장 일보의 유일성이 보장되지 않는다

- 신규 일보 ID가 매번 임의 생성되고 조회 후 생성이 transaction이 아니다.
- Excel 대량 업로드는 같은 날짜·팀·현장이라도 행별 별도 일보를 저장한다.
- 일부 수정 함수는 조회된 첫 번째 일보만 갱신한다.

**운영 영향:** 중복 공수·중복 급여, 일부 일보만 수정되는 현상.

**조치:** `date + teamId + siteId`의 논리 key와 idempotency key를 도입하고 저장 전 전체 중복을 차단한다.

### 11. 현장 조회 실패 또는 오탈자가 신규 마스터로 이어질 수 있다

- site snapshot resolver는 현장을 찾지 못해도 전달된 ID·이름 fallback으로 일보를 저장한다.
- 대량 업로드는 정확한 이름 일치가 없으면 현장과 팀을 자동 생성하며 신규 현장 code를 모두 `AUTO`로 둘 수 있다.
- `siteService.getSiteByName`은 실제로 code 검색 함수를 호출한다 (`siteService.ts:176-178`).

**운영 영향:** 비슷한 이름의 중복 현장·팀, 잘못된 담당팀/회사 귀속, 검색 결과 오인.

**조치:** 자동 생성 금지, 후보 매칭 확인, 회사·주소·담당팀 필수, 중복 name/code 차단을 적용한다.

### 12. 명세서 재발행 기록이 이전 발행본을 덮어쓴다

- `statementOutputService`의 ID는 source/kind/month/statementKey로 고정된다.
- 재발행도 같은 문서를 `setDoc(..., merge: true)`로 갱신하여 기존 snapshot과 issuedAt을 덮는다.
- 실제 인쇄·Excel 생성과 발행이력 기록이 하나의 강제된 원자 흐름이 아니다.

**운영 영향:** 최초 발행본과 재발행본의 차이를 감사할 수 없고, 인쇄했지만 기록이 없는 문서가 생길 수 있다.

**조치:** 발행 건마다 불변 revision 문서를 추가하고 원본 급여 run ID, hash, 발행자, 발행 시각을 저장한다.

## 권한·포털 관련 주의

- `linkedSiteIds` 필드가 없는 레거시 계정은 Rules상 모든 연결회사 현장을 허용하고, 빈 배열은 모든 현장을 차단한다.
- 현장 변경 시 회사 연결과 `linkedSiteIds`가 자동으로 완전 동기화되지 않으면 접근 범위가 기대와 달라질 수 있다.
- `useWorkerAccessScope`는 사용자 프로필을 읽지 못했고 작업자 계정으로 판별되지 않으면 UI상 전체 범위를 구성하는 경로가 있다. Firestore Rules가 최종 방어선이지만 UI도 fail-closed로 바꿔야 한다.
