## 해결한 P0 경로

### 조회와 저장 권한

- 새 날짜 조회 시작 즉시 이전 성공 token 폐기
- pending·reject·stale 응답에서 저장 차단
- URL 날짜와 로컬 날짜 동기화 전 race 차단
- UI disabled와 handler guard가 동일한 승인 조건 사용
- 성공한 현재 request의 날짜·request ID·scope revision·전체 source provenance만 저장 권한으로 인정

### Exact overwrite

- 전체 조회 source를 transaction에서 재검증
- 실제 화면에 표시된 source ID만 삭제
- hidden·unrenderable source는 보존
- source 존재·날짜·팀·현장·createdAt·updatedAt·fingerprint 충돌 시 쓰기 0회
- delete-only exact 저장 지원
- broad `overwriteReports(date, reports, teamIds)`는 명시 오류로 차단

### 원자성과 동시편집

- delete-before-create 제거
- report delete/set과 날짜 scope revision/count를 같은 transaction에서 처리
- 모든 read 완료 후에만 write 등록
- transaction retry 동안 ID와 외부 부수효과 경계 유지
- commit 실패 시 통계·알림·toast 미실행
- commit 후 부수효과 실패가 core commit을 실패로 보이게 하지 않음

### Writer 폐쇄

다음 writer를 strict schema·fingerprint·scope protocol 경계로 전환했다.

- 단일·일괄 생성
- 단일·일괄 수정
- 단일·일괄 삭제
- exact replace
- worker bulk update/delete

다음 위험 경로는 안전한 대체 절차 전까지 fail-closed로 비활성화했다.

- query-then-upsert
- transfer Excel import/reset
- compat daily-report create/update/delete
- UI legacy restore/reset
- 레거시 delete/restore/migration 운영 스크립트

## Scope Protocol

- marker: `daily_report_scope_protocol/active`
- active marker는 정확히 `{version: 1, status: 'active'}`
- scope: `daily_report_scopes/{YYYY-MM-DD}`
- scope 상태: `date`, `revision`, `reportCount`
- malformed·missing old scope·음수·safe-integer overflow 차단
- Rules 접근 호출 예산을 고려해 client atomic write의 영향 날짜를 최대 8개로 제한
- activation은 scan 1/2 fingerprint 비교, scope readback, stale scope 정리 후 active marker를 마지막에 기록
- CLI 출력은 `checkType`, `count`만 허용

## 차단·잔여 위험

### Rules Emulator

Java가 PATH에 없어 Firestore/Storage Emulator allow/deny 검증은 실행하지 못했다. 정적 Rules 테스트는 통과했지만 실제 배포 승인 조건을 대신하지 않는다.

### Scope count 보안 경계

현재 Rules는 old client가 scope를 함께 갱신하지 않는 report write를 차단하고 report root schema·날짜·managed timestamp를 검증한다. 그러나 `canWriteOperations` 권한 사용자의 악의적 scope 단독 변조까지 client Rules에서 완전하게 report mutation과 결합 증명하지 못한다.

따라서 다음 중 하나 전에는 운영 activation을 승인하지 않는다.

1. daily-report mutation을 trusted server callable로 이동
2. Firestore Emulator 기반 추가 결합 검증과 명시적 위험 승인

이 항목은 Phase 5 권한 강화와 연결한다.
