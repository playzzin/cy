# CY V2 팀 월마감 기획서

한 팀의 한 달에 대해 일보와 비용을 검토하고, 작업자 급여와 팀 정산을 각각 확정한 뒤 지급 근거까지 연결한다. 담당자는 한 화면에서 남은 문제와 다음 행동을 찾고, 확정 이후에는 당시 금액을 원천 자료로 재현할 수 있어야 한다.

2026년 10월 3일 사용자가 선택한 범위는 **작업자 급여 + 팀 정산 + 지급 확인**이다. 이 문서는 현재 소스에 근거한 구현 제안이다. 업무 정책과 새 데이터 구조는 candidate이며 운영 적용이나 개발 완료를 의미하지 않는다. 예시 팀과 금액은 모두 가상이다.

## 1 제품 결정

V2의 첫 기능은 **팀 월마감 센터**다. 기존 일보·급여·청구·정산 화면을 업무별 편집 화면으로 재사용하고, 월마감 센터가 검토 대상과 확정본 및 지급 연결을 관리한다.

| 결정 | 기본안 |
| --- | --- |
| 첫 적용 단위 | 선정한 한 팀과 아직 확정하지 않은 한 달 |
| 기간 기준 | Asia/Seoul 기준 업무 발생월. 지급일이 다음 달이어도 원래 귀속월과 연결 |
| 식별 기준 | 회사 범위가 확인된 정식 teamId와 YYYY-MM. 팀 이름은 표시용 |
| 급여와 팀 정산 | 각각 계산·검토하되 하나의 마감 묶음에서 연결 관계를 확인 |
| 확정 기준 | 검토한 계산본과 서버가 확정하는 계산본이 동일해야 함 |
| 지급 기준 | 수취인·대상 채무·금액·일자·근거가 연결된 지급 기록으로 판정 |
| 과거 자료 | 기존 확정본을 보존. 증빙이 부족하면 검증 불가로 표시 |
| 수정 기준 | 확정 전 새 계산본, 확정 후 정정본. 이전 확정본과 지급 기록 보존 |
| 출시 기준 | 핵심 예외 시나리오 통과와 선정한 팀의 독립 금액 대조 완료 |

후속 범위는 은행 자동 송금, 신고 자동 제출, 전체 팀 일괄 마감, AI 자동 승인, 전사 회계원장 구축이다. 이번 범위의 지급 확인은 실제 송금 실행 기능을 포함하지 않는다. 세율과 보험 규칙은 기존 승인된 설정을 사용하고, 새 법정 계산 규칙을 이 기획서에서 정하지 않는다.

## 2 현재 기반과 확장 지점

아래 내용은 운영 데이터가 아닌 현재 소스에서 확인했다. 과거 진행 문서의 체크박스를 현재 구현 상태로 간주하지 않았다.

| 영역 | 확인한 구현 | V2 확장 |
| --- | --- | --- |
| 월급여 | `monthlyPayrollSettlementService.ts`에 draft·reviewed·confirmed·paid 상태와 paymentSnapshot 존재 | 검토본 식별, 지급별 배분, 부분 지급과 정정 연결 |
| 급여 상태 변경 | `transitionRunStatus`는 트랜잭션 사용. draft에서 confirmed로 직접 진행하는 경로도 존재 | V2에서는 검토 완료된 동일 버전만 확정하도록 서버 경계 적용 |
| 팀 정산 | `teamSettlementService.ts`는 system_configs의 team_settlement_ 문서를 사용하고 확정본을 우선 조회 | 새 마감 묶음에 기존 문서 ID와 버전을 명시적으로 연결 |
| 정산 확정 | `saveAndConfirmTeamSettlement`는 확정 직전 자동 항목을 재계산하고 수동 항목을 합침. 관련 테스트 존재 | 변경된 금액을 다시 보여주고 재검토 후 확정. 보이지 않는 금액 교체 방지 |
| 정산 근거 | 지원비 상세 snapshot은 존재. 일보 snapshot은 보고서·현장·팀 중심 | 당시 작업자별 공수·단가·급여형태와 계산 항목까지 저장 |
| 청구 마감 | `supportBillingClosingService.ts`에 카드·차량·숙소 청구의 preview·version·영향 확인 구조 존재 | 공통 마감 점검에 재사용하고 원천 변경 연계 |
| 정산 계산 | 현재 화면은 매출 − 매입 − 공제 + 가산 + 전월 이월 + 입금/정산조정 | 이 계산을 기준으로 대조. 입금/정산조정의 지급 여부는 별도 분류 |
| 일반 지급 기록 | `PaymentRecord`에 일자·입출금·금액·거래처 등이 있으나 마감 revision·개별 급여 채무 배분 필드는 없음 | 실제 채택할 지급 원천을 확인하고 기존 기록을 연결하는 별도 배분 계층 설계 |
| 업무 허브 | `OperationalWorkflowPage.tsx`는 관련 화면으로 이동하는 구조 | 월·팀·검토 항목·처리 결과를 유지하는 업무 흐름으로 확장 |
| 권한 | 월급여와 재무 컬렉션 관련 Rules 및 일부 도메인 보호 구현 존재 | 새 마감·원천 변경·지급 API와 직접 DB 우회까지 통합 검증 |

## 3 사용자의 역할

| 역할 | 수행 업무 | 볼 수 있는 범위 | 확정 권한 |
| --- | --- | --- | --- |
| 팀장 또는 현장 확인자 | 일보·소속·지원 공수 확인, 누락 보완, 이의 제기 | 담당 팀의 업무 자료. 개인별 계좌와 타인 급여 상세는 별도 권한 필요 | 사실 확인만 |
| 급여 및 정산 작성자 | 자료 취합, 귀속 분류, 원천 오류 수정, 계산본 제출 | 담당 범위의 급여·청구·정산 | 검토 요청 |
| 검토 및 확정 담당자 | 금액·증빙·차이 확인, 반려, 마감 확정 | 승인받은 재무 범위 | 검토 완료와 확정 |
| 지급 담당자 | 지급 대상 확인, 근거 연결, 부분 지급·실패·취소 기록 | 지급에 필요한 수취인과 금액 | 지급 확인 |
| 운영 관리자 | 권한 배정, 장애 복구, 정정 절차 관리 | 부여된 관리 범위 | 관리자라는 이유로 금액 검사를 우회하지 않음 |

작성자와 최종 확정자는 다른 사람을 기본안으로 한다. 실제 담당 인원이 한 명인 경우에는 출시 전 업무 책임자가 단독 처리 정책을 선택하고, 해당 건에 정책·사유·처리자를 남긴다. 사용자 이름이나 actorUid를 요청 본문만 믿고 기록하지 않고 인증된 서버 세션에서 확정한다.

## 4 월마감의 상태

**마감 확정은 금액과 근거를 고정하는 행위다. 지급 완료는 연결된 채무가 실제 지급 근거로 해소됐다는 뜻이다.** 두 상태를 별도로 표시한다.

| 마감 상태 | 진입 조건 | 가능한 행동 | 다음 상태 |
| --- | --- | --- | --- |
| 준비 중 | 대상 팀·월 선정 | 자료 조회, 누락 확인, 원천 편집 | 검토 요청 |
| 검토 요청 | 자료 수집 성공, 계산본 생성, 필수 분류 완료 | 작성자 제출, 검토자 확인·반려 | 검토 완료 또는 준비 중 |
| 검토 완료 | 차단 문제 0건, 경고 처리 완료, 검토본 저장 | 동일 검토본 확정 | 마감 확정 |
| 마감 확정 | 서버가 검토본·원천 버전·권한·연결을 다시 검사 | 확정본 조회, 명세서 발행, 지급 연결, 정정 요청 | 정정 진행 |
| 정정 진행 | 이유와 영향 범위를 포함한 정정 요청 | 새 revision 작성·검토·확정 | 새 마감 확정 |

검토 중 원천이나 계산 정책이 바뀌면 `재검토 필요`를 표시하고 기존 검토 승인을 무효화한다. 수정 권한이 없는 사용자는 사유가 포함된 수정 요청을 담당자에게 넘긴다.

지급 상태는 수취인별 채무에서 집계한다: **지급 전 / 일부 지급 / 지급 확인 완료 / 확인 필요 / 수금 대상 / 이월 처리**. 0원 채무는 `지급 대상 없음`으로 표시한다. 음수 잔액은 수금 또는 상계 대상으로 분리하고 음수 송금이나 0원으로 자동 변환하지 않는다. 이월은 지급 완료로 표시하지 않는다.

월의 최종 화면에는 `마감 확정 · 일부 지급`처럼 두 상태를 함께 보여준다. 모든 지급 대상 잔액이 0이고 미확인·중복 지급이 없을 때만 `지급 확인 완료`가 된다.

## 5 담당자의 실제 흐름

1. **팀과 월 선택** — 업무가 발생한 팀 기준으로 대상 목록을 만든다. 현재 소속만 조회해 이동·퇴사자를 빠뜨리지 않는다. 읽기 화면을 열었다는 이유로 초안이나 운영 데이터를 저장하지 않는다.
2. **자료 점검** — 일정 대비 일보, 중복 작업자, 단가, 가불, 회사·팀·개인 부담, 미확정 청구, 지급 근거를 검사한다. 조회 실패와 자료 없음은 다른 상태다.
3. **문제 처리** — 원천으로 이동해 수정하거나 담당자에게 보완을 요청한다. 팀·월·문제 ID를 유지해 마감 화면으로 돌아온다. 새 점검으로 실제 문제가 해결됐을 때만 해소한다.
4. **급여 검토** — 사람별 공수·적용 단가·가산·가불·공제·실지급액을 확인한다. 여러 급여형태와 여러 팀 배분은 동일 인물의 월 기준으로 중복을 검사한다.
5. **팀 정산 검토** — 매출·지원 매입·급여 부담·자원 비용·조정·이월을 확인한다. 급여와 팀 정산에 연결된 동일 비용의 부담·지급 관계를 확인한다.
6. **검토 요청 및 확정** — 새로 집계된 차이를 먼저 보여준다. 검토 완료 후 동일 버전을 확정하고 명세서·정산서·근거 목록을 생성한다.
7. **지급 확인** — 실제 지급 자료를 불러오거나 담당자가 근거와 함께 등록한다. 급여 채무와 팀 정산 채무에 배분하고 부분 지급·불일치를 처리한다.
8. **사후 확인** — 확정본과 지급 잔액을 다시 조회한다. 늦게 도착한 청구나 금액 오류는 영향 범위가 표시된 정정 절차로 처리한다.

자료가 준비된 팀을 대상으로 1~6단계에 걸린 시간, 화면 이동 수, 수동 재입력 수를 파일럿에서 측정한다. 시간 단축 목표는 현재 작업 시간을 측정한 뒤 확정하며, 지금 임의의 단축률을 성과로 약속하지 않는다.

## 6 화면 구성

메뉴명은 **팀 월마감**을 제안한다. 주소는 `/payroll/team-month-close`와 `teamId`, `month` 조회 조건을 사용한다. 기존 화면과 충돌 여부는 구현 착수 시 라우트 등록부에서 확인한다.

### 상단과 공통 영역

- 상단: 팀, 귀속월, 마감 상태, 지급 상태, 마지막 검사 시각, 담당자.
- 금액: 작업자 실지급액, 팀 정산액, 현재 지급 잔액. 서로 다른 성격의 금액임을 라벨로 구분한다.
- 첫 화면: `확정 전 해결할 항목`을 우선 표시한다. 문제마다 대상, 영향, 담당자, 원천 보기 버튼을 둔다.
- 고정된 진행 구간: 자료 점검 → 급여 검토 → 팀 정산 → 확정 → 지급 확인. 다른 구간도 조회할 수 있지만 상태 전이는 조건을 충족해야 한다.

### 주요 화면

| 화면 | 주요 내용 | 주 행동 |
| --- | --- | --- |
| 마감 개요 | 자료별 준비 상태, 차단·경고, 급여·정산 연결 상태 | 문제 검토, 자료 다시 검사 |
| 작업자 급여 | 작업자·기간·소속·공수·금액·급여형태·실지급액·검토 상태 | 근거 보기, 원천 수정, 검토 요청 |
| 팀 정산 | 매출·매입·부담 비용·가산·이월과 이전 계산본 차이 | 비용 귀속 확인, 검토 요청 |
| 최종 검토 | 급여·정산의 동일 계산본, 변경 내역, 미해결 문제, 지급 예정 | 반려, 검토 완료, 마감 확정 |
| 지급 확인 | 수취인별 확정 채무·지급·미지급·근거·지급 방식 | 지급 근거 연결, 배분 확인, 취소·정정 |
| 이력과 문서 | revision별 변경 이유·차이·처리자·명세서와 지급 연결 | 해당 버전 보기, 정정 요청 |

행을 선택하면 근거 상세를 펼친다. 상세에는 적용 일자·공수·단가·부담 대상·원천 문서·계산 규칙·수동 수정 사유를 표시한다. 원천이 없는 금액을 정상으로 보이게 꾸미지 않는다.

모바일에서는 문제 목록과 사실 확인을 우선한다. 큰 급여 표는 작업자별 목록으로 바꾸고, 타인의 급여·계좌를 기본 노출하지 않는다. 데이터 로딩 중·권한 없음·검사 실패·처리 중·충돌 발생·자료 없음의 문구와 행동을 각각 설계한다.

## 7 마감 검사 규칙

검사 결과는 `차단`, `확인 필요`, `정상`, `판단 불가`로 표시한다. 차단 항목과 판단 불가는 단순 확인 체크로 없앨 수 없다. 경고 인정에는 사유와 검토자를 기록하고 계산본이 바뀌면 다시 판단한다.

| 코드 | 조건 | 기본 처리 | 해소 방법 |
| --- | --- | --- | --- |
| SRC_READ_FAILED | 일보·원장·급여 등 필수 원천 조회 실패 | 확정 차단 | 재조회 성공 및 전체 대상 확인 |
| REPORT_MISSING | 배정 일정이 있는데 일보·휴무·취소 설명이 없음 | 해당 범위 확정 차단 | 일보 입력 또는 근거 있는 일정 정정 |
| REPORT_DUPLICATE | 동일 작업·작업자가 중복 계산됨 | 확정 차단 | 중복 원천 정리 후 재검사 |
| RATE_MISSING | 해당 일자의 적용 단가나 필수 급여 설정 없음 | 확정 차단 | 효력일이 있는 승인된 설정 연결 |
| ASSIGNMENT_UNKNOWN | 당시 팀·현장·급여형태를 판정할 수 없음 | 확정 차단 | 근거 있는 수동 귀속 검토 |
| COST_UNALLOCATED | 비용의 회사·팀·개인 부담이 미정 | 확정 차단 | 분류와 배분 합계 확인 |
| COST_DUPLICATED | 하나의 원천 비용이 중복 차감됨 | 확정 차단 | 연결과 배분 수정 |
| BILLING_UNCONFIRMED | 반영 대상 청구가 미확정 | 확정 차단 | 청구 확정 또는 사유 있는 이월 결정 |
| SOURCE_CHANGED | 검토한 뒤 원천의 내용·대상 집합이 변경됨 | 검토 무효화 | 차이 검토 후 새 계산본 제출 |
| MANUAL_ADJUSTMENT | 수기 조정이 있음 | 확인 필요 | 사유·근거·권한 있는 검토 |
| AMOUNT_OUTLIER | 이전 월과 차이가 큼 | 확인 필요 | 사람 수·공수·단가 변화 확인. 임계값은 운영 정책으로 정함 |
| PAYEE_NOT_READY | 지급 계좌·지급 방식 확인 미완료 | 해당 지급만 차단 | 승인된 지급 대상 확인. 금액 마감과 구분 |
| PAYMENT_UNMATCHED | 지급 금액·대상·근거 불일치 | 지급 완료 차단 | 올바른 배분 또는 반제 기록 |
| LEGACY_UNVERIFIABLE | 과거 근거가 없어 재현 불가 | 검증 불가 표시 | 기존 확정본 보존, 수동 확인 수준과 범위 기록 |

회사 부담 비용은 개인이나 팀에 자동 전가하지 않는다. 작업 일정이 없는 날짜를 전부 일보 누락으로 판단하지 않는다. 0원 가불 정정, 감액, 음수 상계는 값과 이력으로 보존한다.

## 8 금액과 연결 규칙

### 작업자 급여

급여 실지급액은 기존 승인된 급여 계산 정책을 적용한 지급총액에서 해당 원천의 가불·공제 등을 반영한 결과다. 일급·월급·용역 등 급여형태에 따라 기존 산식을 유지한다. 공수 × 단가를 모든 급여형태에 일괄 적용하지 않는다.

저장할 값은 산식 입력, 항목별 금액, 부호, 반올림 정책, 적용 설정 버전, 실지급액이다. 합계가 0인 조정도 구성항목을 버리지 않는다. 과거 확정본에 현재 단가나 현재 소속을 대입하지 않는다.

### 팀 정산

현재 화면의 식을 대조 기준으로 유지한다.

`정산액 = 매출 − 매입 − 공제 + 가산 + 전월 이월 + 입금/정산조정`

`summary.deposit`은 현재 `입금/정산조정`이며 위 식에서 가산된다. 실제 지급액이나 선지급액이라고 자동 해석하지 않는다. 첫 적용 전에 대표 사례로 의미를 확정하고, 기존 값과 별개의 지급 연결을 만든다. 분류되지 않은 값이 있으면 담당자가 판단하도록 표시한다.

### 중복 차감과 중복 지급 방지

비용의 **최종 부담자**, 돈을 내는 **지급 주체**, 돈을 받는 **수취인**을 분리한다. 회사가 작업자에게 직접 지급하더라도 그 비용을 팀에 부담시키는 정책일 수 있다. 같은 원천을 급여 채무와 팀 비용에 연결하는 것은 허용하되 같은 채무를 두 번 만들거나 같은 지급 근거를 두 번 배분하지 않는다.

- 원천마다 고유한 sourceId와 sourceRevision을 사용한다. 이름·금액이 같다는 이유로 같은 항목이라 단정하지 않는다.
- 배분의 합계는 승인된 원천 금액과 같아야 한다. 의도적 제외는 금액·사유·검토자를 갖는다.
- 개인 부담 숙소비와 팀 부담 숙소비를 나눴다면 두 배분의 합계와 급여·정산 반영 결과를 함께 검증한다.
- 가불을 급여에서 이미 차감했다면 그 가불 지급 기록을 급여의 남은 실지급액에서 다시 차감하지 않는다.
- 여러 팀에 걸친 작업자는 workerId와 귀속월 및 지급 채무별 전역 배분을 검사한다. 팀별 화면을 독립 처리해도 같은 급여 채무를 중복 확정할 수 없어야 한다.
- 팀 간 지원은 동일 작업 원천과 상대 팀을 연결한다. 양 팀의 표시 방향은 달라도 금액·기간·배분 근거가 일치해야 한다. 상대 팀 확정이 필요한 차이가 남으면 해당 마감을 차단한다.

## 9 검토본과 확정본의 보존

검토본은 다음을 함께 고정한다.

- 팀·귀속월·소속 효력일과 대상 작업자 목록.
- 일보별 작업자·현장·작업일·급여형태·공수·단가·계산 결과.
- 지원비·차량·숙소·카드·가불·수기 조정의 원천 ID와 버전 및 배분.
- 급여 계산본과 팀 정산 계산본의 버전, 적용 정책 버전.
- 원천별 조회 성공 여부, 수집 범위, 개수, 대상 집합 확인값.
- 급여와 정산 합계, 구성항목, 검토 판단과 처리자.

확정 버튼은 검토본 ID를 서버에 전달한다. 서버가 같은 권한·같은 계산본·같은 원천 범위를 확인할 때만 승인한다. 변경을 발견하면 `차량비가 검토 후 변경되었습니다`처럼 차이를 보여주고 다시 검토한다. 자동 재계산한 새 금액으로 조용히 확정하지 않는다.

확정본은 수정 불가이며 명세서·Excel·PDF는 동일 revision에서 생성한다. 문서에 귀속월·발행 버전·발행 시각을 표시하고, 구 버전 재출력과 최신 정정본을 구분한다. 은행 계좌는 제한된 지급 대상 저장소에서 별도 권한으로 관리하고 일반 마감 snapshot·로그에는 원문을 중복 저장하지 않는다.

## 10 지급 확인과 정정

| 상황 | 처리 |
| --- | --- |
| 일부만 지급 | 지급 원장에 금액을 추가하고 배분. 남은 채무 표시 |
| 여러 명을 한 번에 지급 | 지급 묶음의 총액과 수취인별 배분 합계 대조 |
| 같은 근거를 다시 등록 | 동일 요청 ID 및 근거 식별자로 중복 방지. 기존 결과 반환 |
| 이체 실패 | 성공 지급으로 반영하지 않음. 재시도와 실패 기록 보존 |
| 성공 여부 불명확 | 확인 필요로 유지. 단순 재시도로 새 지급을 만들지 않음 |
| 현금 지급 | 지급 방식과 수령 근거, 확인자 기록. 은행 이체 확인과 구분 |
| 은행 알림만 존재 | 연결 후보로 제시. 알림만으로 수취인별 지급 완료 확정 금지 |
| 지급 취소 또는 반송 | 원 지급을 삭제하지 않고 연결된 반제 기록 작성 |
| 지급 대상 계좌 변경 | 별도 확인과 승인. 확정 급여 금액의 변경으로 취급하지 않음 |
| 확정 후 비용 추가 | 원 확정본 유지, 새 정정본과 영향 범위 생성 |
| 지급 후 급여 감액 | 과지급 또는 수금 채무 표시. 이미 지급한 사실 보존 |
| 다음 달 이월 | 이전 채무와 다음 달 배분을 연결. 중복 청구 방지. 지급 완료와 구분 |

부분 지급을 포함한 유효 지급 배분의 합계가 해당 확정 채무를 초과하면 초과 지급 검토가 필요하다. 사용자가 모든 대상을 일괄 paid로 바꾸는 동작을 지급 확인으로 대체한다. 기존 paid 기록에 근거가 없으면 `기존 지급 표시`로 읽고 신규 근거 확인 수준과 구분한다.

정정본은 이전 revision, 정정 사유, 변경 항목, 기존 지급 배분의 유지·추가·반제 내역을 가진다. 기존 지급을 새 정정본에 새 지급처럼 복사하지 않는다. 최종 채무 잔액은 원 채무·정정 증감·유효 지급·반제의 합계로 계산한다.

## 11 데이터와 서버 설계 제안

다음 이름은 신규 구현 제안이며 현재 존재하는 컬렉션이나 API를 의미하지 않는다. 기존 데이터 원천의 이름과 계산 정책은 어댑터에서 명시적으로 연결한다.

| 데이터 | 역할 |
| --- | --- |
| `team_month_closures/{scopeId}` | 팀·월·적용 모드, 현재 revision, 검토·확정 상태, 담당자, 버전 |
| `team_month_closures/{scopeId}/revisions/{revisionId}` | 원천 목록 manifest, 정책 버전, 합계, 검토 결과, 확정자, 준비·완료 상태 |
| `.../revisions/{revisionId}/items/{itemId}` | 작업자 급여·일보 상세·팀 정산 구성항목의 불변 snapshot |
| `.../revisions/{revisionId}/issues/{issueId}` | 검사 규칙, 대상, 영향, 해결 근거, 판단 상태 |
| `payment_obligations/{obligationId}` | 수취인과 귀속 채무, 원 확정본과 정정 관계, 배분 가능 잔액 |
| `payment_records/{paymentId}` | 검증된 지급 사실 또는 기존 지급 원천 참조, 근거, 상태 |
| `payment_allocations/{allocationId}` | 지급 사실과 채무 사이의 배분 및 반제 연결 |
| `closing_source_scopes/{scopeId}` | 관련 원천 변경 세대와 검토·확정 시 충돌 검사 |
| `closing_worker_periods/{workerMonthId}` | 여러 팀에 걸친 동일 작업자 급여와 비용 배분의 중복 검사 |
| `.../events/{eventId}` | 상태 전이·권한 있는 판단·정정·실패의 감사 기록 |

scopeId에는 확인된 회사 범위가 필요하면 포함한다. 현재 프로젝트의 회사별 운영 분리 정책을 먼저 확인한다. 경로 ID에 이름·계좌번호·주민번호를 넣지 않는다. 과도한 단일 문서를 피하도록 상세 항목은 분할 저장한다. Firestore 문서 크기·요청 크기·트랜잭션 한도는 공식 제한을 기준으로 설계한다. [Firestore 제한](https://firebase.google.com/docs/firestore/quotas)

| `recordClosingPayment` | 지급 근거·채무·금액·기존 배분 검증, 멱등 등록 | 중복이면 기존 결과, 불명확하면 상태 조회 |
| `reverseClosingPayment` | 원 지급 참조·사유·권한 확인, 반제 추가 | 원 지급 삭제 금지 |
| `requestClosingAmendment` | 확정본 참조, 정정 이유와 관련 범위 생성 | 기존 확정본 계속 조회 가능 |

서버가 입력·권한·팀 범위·금액·멱등성을 검사한다. Admin SDK 경로는 클라이언트 Rules에만 의존하지 않는다. 클라이언트가 새 확정·지급 문서를 직접 수정할 수 없도록 Rules를 설계하고 허용·거부를 검사한다. [Rules 테스트](https://firebase.google.com/docs/rules/unit-tests)

### 원천 변경과 원자성

1. 일보·급여·가불·청구·배분·단가·소속을 바꾸는 모든 경로를 먼저 목록화한다. 기존 화면, 대량 업로드, 자동 동기화, 복원 도구, 서버 트리거도 포함한다.
2. V2 적용 범위의 원천 변경은 관련 scope 세대를 같은 원자적 변경에 반영한다. 팀 이동이나 팀 간 지원이면 관련된 양쪽 범위와 작업자 월 범위를 검사한다.
3. 계산 후보를 만들기 전 원천 세대 벡터를 읽고, 상세 수집 후 다시 읽는다. 중간 변경이 있으면 후보를 폐기하거나 재시도한다. 대상 문서 추가·삭제도 세대가 바뀌어야 한다. 기존 문서 해시만 비교하는 것으로 누락을 막았다고 판단하지 않는다.
4. 큰 snapshot은 여러 항목으로 준비하고 전체 개수·해시·준비 완료 manifest를 검증한다. 일부 항목만 있는 준비본은 확정할 수 없다.
5. 마지막 트랜잭션은 현재 상태·세대 벡터·검토한 revision·불변 manifest를 재검사하고 확정 포인터·중복 방지 결과·감사 이벤트를 함께 저장한다. 공식 트랜잭션의 재실행 가능성을 고려해 콜백 안에서 알림 발송이나 외부 API 호출을 하지 않는다. [Firestore 트랜잭션](https://firebase.google.com/docs/firestore/manage-data/transactions)
6. 확정 후 원천 정정은 기존 확정 snapshot을 보존하면서 영향 표시와 정정 절차로 이어진다. 원천을 바꿨다는 이유로 과거 출력물이 다시 계산되지 않는다.
7. 미계측 쓰기 경로가 있거나 교차 팀 범위를 보호할 수 없으면 V2 확정을 활성화하지 않는다. 읽기 전용 비교 단계로 남겨 놓는다.

현재 규모에서 순수 계산을 공통 모듈로 분리하고 서버와 검증 테스트가 같은 규칙을 사용하도록 한다. 프론트와 서버에 금액 산식을 별도로 복제하지 않는다. 전체 프레임워크 교체는 이 기능의 출시 선행 조건으로 잡지 않는다.

## 12 기존 기능과의 전환

- 기존 급여·정산·청구 화면과 금액을 비교하는 읽기 전용 센터부터 만든다.
- 팀·월별 적용 모드는 `legacy`, `compare`, `v2`로 둔다. compare에서는 원천 조회와 차이 확인만 제공한다.
- V2 활성 팀·월에 대한 기존 저장·확정·확정 취소 버튼은 서버의 동일 보호 정책을 거치게 한다. 메뉴를 숨기는 것만으로 전환을 완료하지 않는다.
- V2 확정 이후 기존 화면도 같은 revision을 조회하고 같은 버전으로 출력한다. 두 위치에 독립적인 확정 원장을 두지 않는다. 기존 표시용 자료가 필요하면 파생 projection으로만 취급한다.
- 과거 confirmed·paid 기록은 원문과 ID를 유지한다. 없는 상세 근거·지급 근거를 현재 자료로 추정해 채우지 않는다.
- 기존 기능 복귀가 필요해도 V2 확정본은 삭제하지 않는다. 조회·출력 경로와 후속 정정 경로를 유지하고 해당 범위를 legacy 쓰기로 다시 열지 않는다.
- 실제 팀·월 선정, 운영 데이터 전환, 배포는 별도 실행 작업이다. 이 기획 작업에서는 수행하지 않는다.

## 15 출시와 운영 기준

1. 가상 데이터로 정상·교차 팀·늦은 청구·부분 지급·정정 사례를 통과한다.
2. 선정한 팀의 미확정 월을 compare 모드로 대조한다. 실제 개인 자료를 테스트·기획서·로그에 복사하지 않는다.
3. 기존 화면과 새 화면의 차이를 원천 단위로 설명한다. 근거 없는 차이가 하나라도 있으면 확정을 활성화하지 않는다.
4. 검토자·확정자·지급 담당자의 권한으로 실제 동작을 점검한다.
5. 격리된 환경에서 마감과 지급 관계의 복구를 시험한다.
6. 첫 월을 완료한 뒤 다음 월의 이월·정정 연결까지 확인하고 적용 팀을 늘린다.

운영 지표는 미해결 차단 건수, 금액 대조 차이, 근거 없는 지급 건수, 중복 차단 횟수, 원천 변경으로 무효화된 검토 수, 마감 소요시간이다. 식별자·개인 금액 원문을 일반 오류 로그로 내보내지 않는다. 알림은 확정 커밋 이후 재시도 가능한 후속 작업으로 처리하며 알림 실패를 마감 실패로 오표시하지 않는다.

### 화면 초안에서 실제 확인한 항목

2026년 10월 3일 로컬 브라우저에서 가상 데이터로 확인했다.

- 필수 근거 3건이 남아 있을 때 검토 요청 비활성화.
- 원천 보완 예시 적용 후 검토 요청과 검토 완료 및 마감 확정 진행.
- 작업자 급여 5,000,000원 부분 지급 후 총 잔액 29,020,000원에서 24,020,000원으로 감소.
- 작업자 잔액 17,300,000원을 넘는 20,000,000원 입력 차단과 기존 잔액 유지.
- 작업자 잔액과 팀 잔액을 모두 반영한 뒤 총 잔액 0원 및 지급 확인 완료 표시.
- 지급 기록과 검토 및 확정 이력 확인, 급여 계산 근거 펼침 확인.
- 320px 화면에서 급여 표의 목록 전환과 문서 전체 가로 넘침 없음 확인.
- 최종 확인 중 브라우저 콘솔 오류 0건. 예시 산술, 스크립트 문법, 문서의 로컬 소스 링크 11개 검사 통과.

실제 서버 동시성·권한·지급 근거·정정·복구와 AC01~AC22 전체 시나리오는 아직 구현하거나 실행하지 않았다. 이번 파일 변경은 기획서와 화면 초안에 한정된다.
