# 공지·알림 센터 배포 및 검증

## 동작

- 공지 저장과 발송 작업을 서버 트랜잭션에서 함께 기록한다. 동일 사용자·요청 ID는 같은 결과를 반환하며, 다른 내용으로 재사용하면 거절한다.
- 수신 대상은 저장 시점의 활성 사용자, 공지 대상 직책, 자동 발송 설정의 교집합으로 고정한다. 발송 직전 비활성화된 계정은 제외한다.
- 메시지 ID는 작업 ID에서 결정된다. 메시지 생성과 전달 완료 기록도 한 트랜잭션으로 처리한다.
- 발송 실패는 2분부터 최대 60분 간격으로 총 8회 시도한다. 이후 관리자가 전달 현황에서 재시도할 수 있다. 수정·삭제·만료된 공지의 오래된 예약은 취소한다.
- 이미 발송한 공지를 수정하면 이전 알림을 보관 상태로 바꾼다. 새로 보내는 확인 요청은 별도 확인 기록을 갖는다. 공지 삭제 후에는 서버 트리거가 관련 알림을 보관 처리한다.
- 읽음은 기존 메시지 수신 확인이고, 확인 완료는 수신자별 별도 기록이다. 관리자는 두 상태를 구별해 조회한다.
- 다시 알림은 개인 상태에 저장한다. 예약 시간에 본인의 읽음 기록만 해제한다. 다른 사람의 읽음과 확인 완료에는 영향을 주지 않는다. 1분 주기 작업으로 처리하므로 실행 지연이 있을 수 있다.
- 종류별 표시, 소리·진동, 한국 시간 기준 방해 금지, 일반 알림 소리 묶음 설정을 계정에 저장한다. 종류를 꺼도 전체 목록에는 남으며, 확인 완료 요청은 표시를 유지한다. 소리·진동과 묶음 처리는 앱이 열린 동안 적용된다.
- 오늘 기한은 기한이 포함된 공지 확인 요청 및 할일 알림을 기준으로 표시한다. 기존 기한 없는 알림은 역산하지 않는다. 할일의 최신 처리 상태는 원문에서 확인한다.
- 발송 현황의 전달 완료는 앱 내 알림함 저장을 의미한다. 푸시·SMS·이메일 수신을 의미하지 않는다.

## 배포 범위

사용자 승인 후 기존 프로젝트 배포 절차에 따라 다음을 함께 반영한다.

1. firestore.indexes.json의 notice_notification_outbox(status, nextAttemptAt), notification_user_states(reminderStatus, snoozedUntil) 인덱스를 생성하고 준비 상태를 확인한다.
2. asia-northeast3의 다음 함수를 배포한다.
   - saveNoticeWithNotification
   - setPersonalNotification
   - saveNotificationPreferences
   - getNoticeDeliveryReport
   - retryNoticeDelivery
   - dispatchNoticeNotification
   - recoverNotificationDeliveries
   - archiveDeletedNoticeNotifications
   - notifyTaskChanges (기한 메타데이터 추가)
3. 검증된 프런트엔드 빌드와 firestore.rules를 반영한다. 새 함수 없이 프런트엔드만 배포하면 공지 저장과 개인 처리가 실패한다.
4. 이전 화면을 열어둔 관리자는 새로고침한다. 공지 직접 쓰기는 새 규칙에서 차단되므로 예전 화면에서는 저장할 수 없다.
5. 공지 발송 설정이 켜져 있고 대상 사용자가 있는지 확인한다. 필수 확인 공지는 수신 대상이 없거나 발송 설정이 꺼진 경우 저장 단계에서 거절한다.

## 검증

- 프런트엔드 관련 Jest 테스트, 전체 typecheck, 변경 파일 ESLint, 운영 빌드와 hosting-build 검증.
- Functions 빌드 및 기존 taskNotifications, smartMemoReminders 단위 테스트.
- scripts/test-notification-center.mjs: Firestore/Auth 에뮬레이터 전용. 원자적 저장, 동시 요청, 재시도, 개인 상태 격리, 권한, 기한, 설정, 관리자 현황, 페이지 경계를 검사한다.
- scripts/test-notice-notification-rules.mjs: 기존 직접·전체 메시지 읽음과 보호된 시스템 알림 권한을 검사한다.
- 브라우저 미리보기는 샘플 데이터로 동작한다. 실제 서버 권한·예약 실행은 에뮬레이터 시험으로 별도 검증한다.
- 운영 배포 후 승인된 시험 계정으로 공지 저장 → 발송 완료 → 읽음 → 확인 완료 → 다시 알림 → 전달 현황을 확인해야 한다. 운영 Scheduler/IAM, 실제 트리거와 네트워크 상태는 로컬 검증만으로 보장하지 않는다.

## 제한 및 복구

- 공지당 최대 2,000명. 초과 시 저장 전에 대상을 나누도록 안내한다.
- 전달 현황은 이 기능 적용 후의 발송부터 제공한다. 과거 기록이나 확인 완료 시각을 만들어 채우지 않는다.
- 예약 작업이 멈추면 Scheduler 및 Functions 로그를 확인한다. 실패 작업은 전달 현황에서 재시도한다. 같은 작업을 재시도해도 이미 만든 메시지는 중복 생성하지 않는다.
- 이전 프런트엔드로 되돌릴 때는 공지 직접 쓰기 규칙과 서버 의존성도 함께 검토한다. 수신 기록·발송 작업은 삭제하지 않는다.
